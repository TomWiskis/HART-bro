# HART-бро 0.3.0 — журнал, отчёты и управление сессиями

**Проект:** https://github.com/TomWiskis/HART-bro  
**Исходная версия:** 0.2.1  
**Целевая версия:** 0.3.0  
**Основной транспорт:** Bluetooth Classic SPP  
**Модем:** Pepperl+Fuchs VIATOR  
**Основной испытательный прибор:** Метран-150, HART 7

## 1. Общая задача

Продолжить разработку существующего приложения, не создавая новый проект.

Основные задачи версии:

1. Разделить подключение коммуникатора и запуск измерительной сессии.
2. Исправить нестабильность мониторинга при переключении между Android-приложениями.
3. Реализовать полноценный журнал проверок.
4. Добавить экспорт PDF и CSV.
5. Реализовать чтение настроенного диапазона измерений.
6. Показывать настроенный диапазон на графике одной компактной строкой.
7. Добавить сохранение и сравнение доступных конфигурационных параметров.
8. Сохранить все уже работающие возможности 0.2.1.

Новые функции HART-записи, калибровки и USB OTG в этой версии не реализовывать.

## 2. Результаты испытания 0.2.1

Пользователь проверил приложение на Android 16 с реальным Метран-150.

Подтверждены:

- Успешная идентификация HART 7.
- Manufacturer `0x0099`.
- Device Type `0x9972`.
- Device ID `5FCA7F`.
- Успешное чтение HART-команд 0, 1, 3, 8, 9, 48 и 50.
- Корректный приём фрагментированных сообщений.
- Непрерывный опрос цифровых измерений.
- Отображение графика с единицами измерения.
- Работа автоследования.
- Успешное восстановление после отдельного разрыва Bluetooth.
- Работа паузы и возобновления опроса.

### Неустранённые недостатки

**А. Отсутствие отдельного запуска сессии.**

Сейчас сессия автоматически создаётся при подключении Bluetooth-модема. Пользователь хочет иметь отдельную кнопку запуска измерительной сессии.

**Б. Нестабильная работа в фоне.**

При переключении в другие приложения мониторинг иногда прерывается.

В присланном HEX-журнале наблюдается следующее:

- `13:40:42` — Activity уходит в фон, служба продолжает работать.
- `13:40:54` — таймаут HART-команды 9.
- Далее — восстановление нормального опроса.
- `13:41:03–13:41:10` — при другом переключении опрос успешно продолжается.
- `13:42:09` — Activity уходит в фон во время нового подключения.
- `13:43:33` — после возвращения состояние `ERROR`, успешная идентификация не выполнена.

Нельзя утверждать, что причиной является исключительно завершение foreground service. Необходимо установить причину нестабильности по диагностике.

Основной принцип: не переписывать уже работающий HART-движок ради исправления жизненного цикла Android.

# 3. Разделение подключения и измерительной сессии

Это обязательное изменение версии 0.3.0.

### 3.1. Подключение коммуникатора

На вкладке «Связь» оставить выбор и подключение Bluetooth VIATOR.

После подтверждения пользователя:

1. Установить Bluetooth SPP-соединение.
2. Выполнить идентификацию подключённого HART-датчика.
3. Показать информацию об устройстве.
4. Перейти в состояние готовности к мониторингу.

**Само подключение больше не должно автоматически создавать измерительную сессию.**

Разовое чтение параметров для определения прибора допускается.

### 3.2. Кнопка «Начать сессию»

На вкладке «Монитор» добавить явно доступную кнопку:

**Начать сессию**

При нажатии:

- Создать новую временную историю.
- Зафиксировать идентификатор HART-прибора.
- Зафиксировать дату и время.
- Сохранить снимок доступной конфигурации.
- Запустить периодический опрос.
- Начать построение графика.

Если устройство уже подключено, новое подтверждение Bluetooth не требуется.

Если прибор не идентифицирован или связь отсутствует, показать понятное сообщение и предложить перейти к подключению.

### 3.3. Пауза

Кнопка «Приостановить» останавливает измерительный опрос, но сохраняет Bluetooth-соединение и саму сессию.

«Продолжить» возобновляет её.

### 3.4. Завершение сессии

Пользователь выбирает:

- Сохранить сессию.
- Завершить без сохранения.

После этого:

- Периодический опрос останавливается.
- Временная история обрабатывается согласно выбору.
- Bluetooth-соединение может остаться открытым.
- На вкладке «Монитор» снова доступна кнопка «Начать сессию».

Таким образом, можно выполнить несколько отдельных проверок через одно Bluetooth-подключение.

### 3.5. Новая сессия после завершения старой

Перед началом следующей сессии необходимо повторно проверить HART-идентификатор прибора.

Если датчик изменился, новая сессия должна относиться к новому устройству.

Не объединять данные разных датчиков.

Полностью автоматическое обнаружение следующего датчика после перестановки щупов — отдельный будущий режим «Обход датчиков», не входящий в 0.3.0.

# 4. Исправление фонового мониторинга

## 4.1. Обязательное поведение

После запуска измерительной сессии пользователь может:

- Выключить экран смартфона.
- Нажать Home.
- Открыть другое приложение.
- Перейти в браузер или Telegram.
- Вернуться к HART-бро.

Во всех этих случаях опрос должен продолжаться, пока Android разрешает работу активной foreground service.

При возврате на графике должны находиться измерения за время отсутствия пользователя в интерфейсе.

Нельзя запускать новую измерительную сессию при возвращении Activity.

## 4.2. Архитектура

Проверить и при необходимости исправить:

- Владение Bluetooth-сокетом.
- Владение очередью HART-команд.
- Coroutine scope мониторинга.
- `MonitoringService`.
- `SessionViewModel`.
- Обработку жизненного цикла Activity.
- Сохранение состояния при переходе приложения в фон.
- Запуск нового подключения, пока Activity не видима.
- Ошибки начального Bluetooth-соединения.

Foreground service должна владеть активным мониторингом независимо от отображаемого экрана.

Activity должна быть потребителем состояния, а не необходимым условием существования сеанса.

## 4.3. Диагностика

Добавить отдельную техническую регистрацию:

- Время ухода Activity в фон.
- Время возвращения.
- Состояние foreground service.
- Состояние Bluetooth-сокета.
- Время последнего TX.
- Время последнего RX.
- Время последнего успешного HART-измерения.
- Длительность периода отсутствия измерений.
- Причину перехода в ERROR.
- Причину закрытия сокета и его инициатора, насколько это позволяет установить приложение.

Не выводить предположительные причины как установленные факты.

При потере обмена сохранить существующую логику восстановления связи до 60 секунд.

Не создавать повторное Bluetooth-подключение, если исходное соединение исправно.

## 4.4. Приёмочные испытания

Обязательные сценарии:

1. Мониторинг с включённым экраном в течение 5 минут.
2. Мониторинг с выключенным экраном в течение 5 минут.
3. Мониторинг при работе другого приложения в течение 5 минут.
4. Несколько последовательных переключений между приложениями.
5. Возврат к HART-бро без потери состояния.
6. Переход в другое приложение во время первоначального подключения.
7. Контролируемая кратковременная потеря HART-ответов.

Проверять не только существование фоновой службы, но и фактическое поступление новых данных.

# 5. Чтение настроенного диапазона измерений

Добавить чтение настроенных границ диапазона первичной переменной.

Для стандартных HART-устройств использовать команду №15 — `Read Device Information`.

Из ответа получать:

- Единицу диапазона.
- Нижнюю настроенную границу.
- Верхнюю настроенную границу.
- Другие доступные поля команды, если они нужны для снимка конфигурации.

Использовать корректные структуры HART для соответствующей ревизии устройства.

Все полученные данные сохранять без потери исходной точности.

Если команда не поддерживается или ответ недостоверен, показывать «Диапазон неизвестен».

Не вычислять диапазон из минимального и максимального значения графика.

Не вычислять диапазон из измеренного тока 4–20 мА.

Не путать настроенный диапазон с физическими пределами сенсора.

## 5.1. Отображение на графике

В правом верхнем углу графика мелким шрифтом показывать одну строку:

`0…40 кПа`

Другие примеры:

`−50…150 °C`

`0…2,5 МПа`

Не подписывать отдельно LRV и URV.

Не показывать пределы сенсора.

Не добавлять отдельную большую таблицу диапазонов в монитор.

Информационная строка не должна перекрывать график, подписи осей или другие элементы.

## 5.2. Пределы сенсора

Физические пределы сенсора планируется показывать в будущем режиме изменения диапазона.

В версии 0.3.0 их не требуется выводить.

# 6. Полноценный журнал проверок

Развить существующее хранилище сохранённых сессий.

Каждая сохранённая проверка должна включать:

- Внутренний ID записи.
- Название проверки.
- Дату и время начала.
- Дату и время окончания сохранённого интервала.
- Длительность.
- Название Bluetooth-коммуникатора.
- Идентификатор HART-датчика.
- Производителя.
- Тип устройства.
- TAG, если получен.
- Настроенный диапазон.
- Единицы измерения.
- Снимок доступной конфигурации.
- Полную исходную историю измерений.
- Статусы качества.
- Интервалы потери связи.
- События сессии.
- Комментарий пользователя.

Все данные проверки должны оставаться доступными без подключения датчика.

## 6.1. Список проверок

На вкладке «Журнал» показывать компактные записи.

Основные поля:

- Дата.
- TAG или идентификатор прибора.
- Производитель.
- Настроенный диапазон.
- Длительность.

Добавить поиск по TAG, ID и пользовательскому названию.

Предусмотреть сортировку по дате и названию.

## 6.2. Действия с проверками

Пользователь может:

- Открыть проверку.
- Переименовать запись.
- Добавить или изменить комментарий.
- Посмотреть график.
- Посмотреть снимок конфигурации.
- Экспортировать PDF.
- Экспортировать CSV.
- Удалить запись.

Для удаления необходимо отдельное подтверждение.

Добавить возможность выбрать несколько проверок для удаления.

Предусмотреть очистку всего журнала с явным подтверждением.

## 6.3. Важно

**Проверки сохраняются только по явному действию пользователя.**

Не добавлять автоматическое постоянное сохранение всех сеансов.

Повторное сохранение во время действующей сессии создаёт самостоятельный снимок и не останавливает мониторинг.

# 7. Экспорт PDF

Реализовать создание полноценного отчёта по сохранённой проверке.

PDF должен содержать:

### Заголовок

- Название HART-бро.
- Дату проверки.
- Пользовательское название записи.

### Данные прибора

- Производитель.
- Тип устройства.
- Device ID.
- TAG.
- Версия HART.
- Настроенный диапазон.
- Bluetooth-коммуникатор.

### Данные измерений

- Длительность.
- Перечень цифровых измеряемых переменных.
- Единицы измерения.
- Минимальные и максимальные полученные достоверные значения.
- Средние значения, если они рассчитываются по подтверждённым исходным измерениям.
- Количество достоверных точек.
- Информация о пропущенных интервалах.

### График

Поместить единый график измерений с:

- Временной осью.
- Числовыми делениями.
- Единицами.
- Легендой.
- Реальными разрывами измерений.

PDF должен оставаться читаемым при печати на A4.

### Дополнительные сведения

- События потери и восстановления связи.
- Ошибки измерений.
- Пользовательский комментарий.

Не включать выдуманные или восстановленные измерения.

Если какие-то данные отсутствуют, обозначать их отсутствие.

Экспорт выполнять локально, без интернета.

Пользователь самостоятельно выбирает место сохранения или приложение для отправки файла через стандартные механизмы Android.

# 8. Экспорт CSV

CSV должен обеспечивать работу с Microsoft Excel и другими табличными программами.

Обязательные поля:

- Временная метка.
- Идентификатор прибора.
- Код/название переменной.
- Числовое значение.
- Единица измерения.
- Код единицы HART.
- Качество измерения.
- Номер команды, из которой получено значение.

Не округлять значения до записи.

Использовать UTF-8 с корректной обработкой кириллицы.

Предусмотреть явное указание разделителя и корректное экранирование полей.

Для совместимости с региональными настройками Excel можно предложить вариант CSV с `;` в качестве разделителя.

Временные метки должны иметь однозначный формат с датой, временем и часовым смещением либо UTC.

События связи можно экспортировать отдельным CSV-файлом.

Не заменять отсутствующие измерения нулями.

Не создавать автоматически ложные промежуточные точки.

# 9. Снимок конфигурации

Во время подключения или начала сессии считывать доступные параметры конфигурации исключительно командами чтения.

На этом этапе достаточно стандартизированных данных, например:

- Идентификация — команда 0.
- TAG и описание — поддерживаемые команды 13 и 20.
- Настроенный диапазон — команда 15.
- Демпфирование — при наличии в ответе соответствующей команды.
- Дополнительные диагностические сведения — команда 48.
- Назначение переменных — команда 50.
- Другие уже поддерживаемые поля.

Если отдельная команда не поддерживается, не завершать всю сессию.

Сохранять источник каждого параметра.

Не считать неполный снимок полной конфигурацией датчика.

## 9.1. Сравнение конфигураций

Добавить сравнение двух сохранённых проверок, а также текущих прочитанных параметров с сохранённой проверкой.

Представлять сравнение в виде таблицы:

| Параметр | Проверка А | Проверка Б |
|---|---|---|
| TAG | Доступное значение | Доступное значение |
| Диапазон | Доступное значение | Доступное значение |
| Единица | Доступное значение | Доступное значение |
| Демпфирование | Доступное значение | Доступное значение |

Отличающиеся настройки выделять.

Если параметр отсутствует в одном снимке, показывать «Нет данных», а не считать его изменённым.

**Фактическое давление, температуру и другие текущие измерения не считать параметрами конфигурации.**

Полноценное сравнение всех специфических настроек различных производителей реализовать позднее, вместе с расширенным конфигурированием.

# 10. Сохранение обратной совместимости

Все сохранённые записи 0.2.0 и 0.2.1 должны оставаться доступными.

Не удалять старые архивы при обновлении приложения.

Если меняется формат хранения:

- Реализовать версионирование.
- Поддержать чтение старых форматов.
- При необходимости выполнить безопасную миграцию.
- Предусмотреть тестирование старых архивных файлов.

Если старая запись не содержит диапазона или конфигурации, показывать отсутствие данных.

Не придумывать исторические настройки.

Для новых данных конфигурации предусмотреть хранение исходных HART-кодов, единиц и метаданных, позволяющее расширять формат без потери существующих записей.

# 14. План аппаратного испытания 0.3.0

Подготовить один комплексный сценарий проверки с Метран-150.

**Проверка 1. Подключение**

Подключиться к VIATOR, убедиться, что HART-датчик определён, но измерительная сессия ещё не началась.

**Проверка 2. Начало сессии**

Нажать «Начать сессию» и убедиться в запуске непрерывного опроса.

**Проверка 3. Диапазон**

Проверить чтение команды 15 и сравнить настроенный диапазон с фактической конфигурацией Метрана.

**Проверка 4. График**

Запустить опрос на 3–5 минут, проверить значения и единицы.

**Проверка 5. Работа в фоне**

Открыть другое Android-приложение на пять минут, затем вернуться и проверить фактическую непрерывность опроса.

**Проверка 6. Сохранение**

Сохранить сессию и открыть её в журнале.

**Проверка 7. PDF**

Экспортировать отчёт и проверить график, шкалы и сведения о датчике.

**Проверка 8. CSV**

Экспортировать измерения и проверить значения, временные метки и единицы.

**Проверка 9. Повторная сессия**

Завершить текущую сессию, оставить Bluetooth-соединение открытым и начать новую без повторного подключения VIATOR.

**Проверка 10. Диагностика**

Сохранить полный HEX-журнал и проверить наличие первоначальной команды 0, команды 15, измерительных команд и событий Android.

Не проводить операции записи в датчик.

# 15. Будущие возможности, которые пока не реализовывать

## Режим «Обход датчиков»

В будущем нужен специальный режим последовательной проверки множества датчиков на клеммнике.

Алгоритм:

- Bluetooth VIATOR подключается один раз.
- Пользователь переставляет HART-щупы.
- Приложение автоматически идентифицирует новый прибор.
- Без нажатия «Опросить» считывает TAG, идентификатор и настроенный диапазон.
- Показывает компактную карточку.
- Ожидает следующего датчика.
- Не воспринимает снятие щупов как критическую потерю Bluetooth.
- По запросу пользователя сохраняет таблицу результатов обхода.

Предпочтительное отображение диапазонов:

`0…40 кПа`

`−50…150 °C`

Без отдельных полей LRV/URV в основном интерфейсе.

## Запись диапазонов

Будущий экран конфигурирования должен позволять изменять настроенный диапазон только после явного подтверждения.

Именно там должны показываться физические пределы сенсора и допустимость введённых значений.

## USB OTG

Будущая поддержка ЭнИ-406, настольного исполнения, без встроенного питания датчика, с mini-USB.

Не реализовывать USB сейчас.
