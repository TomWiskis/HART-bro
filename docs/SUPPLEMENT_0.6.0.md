## 1. Исправление идентификации Метран-150R

### 1.1. Выявленная проблема

При реальных испытаниях приложение определяет некоторые датчики Метран как Rosemount.

Анализ HEX-журналов подтвердил, что приборы возвращают:

- Manufacturer ID: `0x0026`.
- Device Type: `0x2662`.
- Device Revision: `9`.
- HART Revision: `5`.

По официальному реестру FieldComm Group такая комбинация соответствует **Metran-150R**.

Текущее приложение использует название производителя по его HART-коду, не учитывая зарегистрированную модель.

Из-за этого в карточках и экспортируемых таблицах вместо Метран-150R появляется Rosemount.

### 1.2. Требуемое исправление

Реализовать идентификацию модели по сочетанию:

`Manufacturer ID + Device Type + Device Revision`

Для комбинации:

`0x0026 / 0x2662 / Rev 9`

отображать:

**Метран-150R**

При этом не изменять исходные HART-идентификаторы.

В подробной диагностике сохранить:
- Исходный Manufacturer ID.
- Название зарегистрированного производителя.
- Device Type.
- Device Revision.
- Расшифрованную модель.

Учитывать, что зарегистрированный производитель по HART и коммерческое название устройства могут различаться.

### 1.3. Таблицы производителей и моделей

Расширить ранее запланированный справочник идентификации.

Поддерживать:
- Код производителя.
- Название производителя.
- Код устройства.
- Ревизию устройства.
- Название модели.
- Источник идентификационных данных.

Не определять модель только по Manufacturer ID.

Не присваивать неизвестным комбинациям названия похожих устройств.

При отсутствии совпадения в справочнике отображать известную информацию и исходные коды.

Пример: неизвестную комбинацию `0x00FA / 0xFAEC` сохранять без выдуманной расшифровки.

### 1.4. Применение

Исправленная идентификация должна использоваться во всех режимах:

- Быстрый просмотр.
- Измерительная сессия.
- Диагностика.
- Обход датчиков.
- Экспорт XLSX.
- Экспорт диагностических данных.

Не создавать отдельные, несогласованные таблицы моделей для разных экранов.

## 2. Исправление неудачной идентификации HART

### 2.1. Обнаруженная проблема

Анализ журнала «ж6 не нашел датчик(1).txt» выявил случаи, когда приложение не могло определить подключённый датчик.

При этом Bluetooth-соединение с VIATOR оставалось работоспособным.

Зафиксированы следующие ситуации:

**Ситуация № 1 — отсутствие ответа**

Приложение отправляет Command 0, ожидает ответ и получает таймаут.

После первой неудачной попытки первоначальное подключение иногда сразу завершается ошибкой.

При повторном запуске опроса тот же датчик успешно определяется.

**Ситуация № 2 — повреждённый HART-кадр**

03.11.2026 в 04:34:42 UTC:

- Получен ответ на Command 0.
- Проверка XOR выявила несоответствие.
- Кадр отклонён.
- По окончании таймаута приложение завершило идентификацию ошибкой.
- В 04:34:49 повторная попытка успешно определила датчик.

**Ситуация № 3 — неполный HART-кадр**

В 01:33:58 UTC приложение получило начало ответа Command 0, но до истечения таймаута полный кадр не был собран.

Опрос завершился ошибкой отсутствия ответа.

**Ситуация № 4 — длительная потеря HART-связи**

В 02:19:59–02:20:59 UTC выполнялись повторные попытки восстановления связи.

За установленное время корректный HART-ответ не был получен.

### 2.2. Повторная первоначальная идентификация

Изменить алгоритм начального подключения.

Если транспорт подключён, но Command 0 не выполнена успешно:

1. Не переводить подключение немедленно в окончательное состояние ERROR.
2. Выполнить повторную попытку.
3. Разрешить до трёх последовательных попыток первоначальной идентификации.
4. Между попытками использовать короткую ограниченную паузу.
5. При первом корректном ответе сразу переходить к чтению конфигурации.
6. После исчерпания попыток показывать понятную ошибку.

Не выполнять бесконечные циклы начального подключения.

**Важно:** правило трёх попыток относится к первоначальному разовому подключению. В режиме обхода, где уже выполняется периодический поиск датчика, не добавлять по три вложенных запроса на каждый цикл обнаружения. Сохранить ранее согласованную оптимизацию обхода.

### 2.3. Разделение ошибок

В HART-движке и диагностическом журнале различать:

- Отсутствие каких-либо данных после запроса.
- Неполный кадр к моменту таймаута.
- Неверную контрольную сумму XOR.
- Некорректную длину кадра.
- Некорректный адрес.
- Неверный номер команды в ответе.
- Ошибку HART, возвращённую самим датчиком.
- Физическую потерю Bluetooth/USB-транспорта.

Не использовать одинаковое сообщение «датчик не отвечает» для всех перечисленных ситуаций.

Если физический транспорт работает, а HART-кадр повреждён, отображать ошибку HART-обмена, а не потерю Bluetooth.

### 2.4. Проверка целостности

**Никогда не принимать кадры с неверной XOR.**

Не пытаться определять устройство по частично принятому кадру.

Не отключать проверку XOR ради ускорения или повышения процента успешных обнаружений.

Сохранить поддержку ответов с четырьмя байтами преамбулы FF, ранее подтверждённую реальными испытаниями.

Не считать допустимую короткую преамбулу причиной ошибки всего кадра.

### 2.5. Таймауты

Не уменьшать безусловно таймаут чтения до 1500 мс для всех команд.

В журнале обнаружены случаи незавершённого приёма к границе этого времени.

Разделить настройки:
- Таймаут начальной идентификации.
- Таймаут периодического поиска при обходе.
- Таймаут обычного чтения.
- Таймаут восстановления соединения.

Сокращение пауз между попытками обнаружения оставить согласно основному ТЗ.

Вести измерение фактической длительности запросов.

Не считать любой таймаут доказательством неисправности датчика.

### 2.6. Восстановление связи

Сохранить существующее окно восстановления до 60 секунд.

При успешном восстановлении:
- Проверять идентификатор устройства.
- Не подменять данные одного датчика данными другого.
- Восстанавливать соответствующий режим работы.
- Корректно обновлять индикатор состояния.

Если восстановление не удалось, не удалять ранее полученную информацию.

Не выполнять автоматические повторы команд записи после неопределённого результата.

## 3. Обязательная универсальная установка нуля

### 3.1. Назначение

Реализовать полноценную установку нуля через HART.

Операция предназначена для компенсации нулевого смещения датчика давления при правильно приложенном нулевом или эталонном воздействии.

Это **обязательная функция текущей версии 0.6.0**, а не задача будущих этапов.

Она должна работать через:
- VIATOR Bluetooth.
- ЭнИ-406 USB OTG.

Использовать единый механизм выполнения команд через общий HART-движок.

### 3.2. Доступность

Предоставлять кнопку «Установить ноль» для всех распознанных датчиков давления.

Включая:
- Метран.
- Rosemount.
- Других известных производителей.
- Неизвестные модели.
- Датчики без доступного Device Description.
- Приборы, поддержка установки нуля у которых заранее неизвестна.

**Не использовать справочник моделей как обязательное разрешение на выполнение стандартной команды установки нуля.**

Отсутствие информации о поддержке не означает, что прибор не поддерживает команду.

Не скрывать кнопку только потому, что модель отсутствует в локальной базе.

### 3.3. Стандартная команда

Первоначальный метод:

**HART Command 43 — Set Primary Variable Zero.**

Реализовать формирование и передачу стандартного запроса.

Для Command 43:
- Использовать корректный адрес текущего прибора.
- Не отправлять дополнительные данные, если они не предусмотрены форматом команды.
- Не изменять LRV и URV вместо установки нуля.
- Не выполнять калибровку аналогового выхода 4–20 мА.
- Не выполнять автоматическую повторную запись после таймаута.

Команду разрешено отправлять на неизвестную модель датчика давления после явного подтверждения пользователя.

### 3.4. Обработка результата

Не предполагать успешность команды заранее.

Возможные результаты:
- Операция выполнена.
- Команда не поддерживается.
- Защита записи.
- Недопустимые условия калибровки.
- Давление вне разрешённого диапазона.
- Устройство занято.
- Ошибка производителя.
- Отсутствие ответа.
- Повреждённый ответ.

Выводить понятное сообщение и сохранять исходный код ответа в диагностическом журнале.

Если прибор сообщает, что команда не поддерживается, считать это результатом испытания конкретного устройства, но не исключать команду для всех датчиков данного производителя.

Отсутствие ответа не считать доказательством отсутствия поддержки.

### 3.5. Последовательность операции

При нажатии «Установить ноль»:

1. Убедиться, что выбран конкретный датчик.
2. Проверить действующее HART-соединение.
3. Показать предупреждение о необходимости создать правильные условия калибровки.
4. Прочитать текущую PV, если доступна.
5. Запросить отдельное подтверждение пользователя.
6. Отправить Command 43.
7. Принять и расшифровать ответ.
8. При успешном ответе повторно прочитать PV.
9. Проверить результат с учётом разрешения и допустимой погрешности датчика.
10. Записать операцию в журнал изменений.

В журнале сохранять:
- Дату и время.
- Идентификатор прибора.
- Использованный коммуникатор.
- Номер команды.
- PV до операции, если получена.
- HART-код результата.
- PV после операции, если получена.
- Итог проверки.

Если прибор подтвердил выполнение команды, но контрольное измерение недоступно, показывать «Команда принята, результат измерением не подтверждён».

Не объявлять результат успешным только по факту передачи запроса.

### 3.6. Безопасность

Установка нуля — операция калибровки, изменяющая настройки прибора.

Не выполнять её автоматически при подключении, обходе или диагностике.

Не выполнять процедуру без подтверждения пользователя.

Не повторять команду после таймаута автоматически, поскольку она могла быть выполнена, несмотря на потерю ответа.

Не смешивать:
- Установку нуля датчика.
- Изменение нижнего предела измерения.
- Изменение диапазона.
- Коррекцию аналогового выхода.

Для дифференциальных, избыточных и абсолютных датчиков обеспечивать разные предупреждения об условиях калибровки, если тип измерения известен.

При неизвестном типе показывать общее предупреждение без предположения, что атмосферное давление соответствует физическому нулю.

- Формат параметров.
- Назначение команды.
- Ожидаемые ответы.
- Условия применения.
- Источник сведений.
- Статус проверки на реальном датчике.

Не считать одно совпадение Manufacturer ID достаточным основанием для применения специфической команды записи.

## 5. Исследование HART-команд через сторонний коммуникатор

### 5.1. Назначение

Предусмотреть возможность определить неизвестную команду установки нуля посредством анализа обмена между датчиком и другим HART-коммуникатором.

Пользователь может выполнить установку нуля штатным коммуникатором, а HART-бро должен помочь записать и расшифровать обмен.

Это необходимо для датчиков, у которых:
- Нет доступной документации.
- Неизвестен алгоритм калибровки.
- Не поддерживается стандартная Command 43.
- Используется специфическая процедура производителя.

### 5.2. Режим прослушивания

Добавить диагностическую возможность **«Прослушивание HART»** при наличии соответствующей аппаратной поддержки.

Режим должен:
- Работать без отправки собственных HART-запросов.
- Получать доступные модему HART-кадры стороннего обмена.
- Не вмешиваться в выполнение сторонней команды.
- Сохранять запросы и ответы.
- Записывать точное время получения.
- Отображать HEX.
- Расшифровывать номер команды, адрес, данные, статус и XOR.
- Позволять экспортировать журнал.

### 5.3. Проверка аппаратной возможности

Не предполагать заранее, что VIATOR или ЭнИ-406 умеет пассивно принимать чужие HART-запросы.

Исследовать возможности обоих модемов.

Если пассивный приём недоступен:
- Чётко указать аппаратное ограничение.
- Не имитировать прослушивание программно.
- Предусмотреть импорт и расшифровку HEX-журнала, полученного совместимым HART-анализатором.

Не изменять прошивку модема ради этой функции в рамках текущего этапа.

Не подключать второй активный HART-master без проверки допустимости такого режима и соблюдения требований к линии.

### 5.4. Анализ неизвестной команды

В режиме анализа предоставлять:
- Отображение всех полученных команд.
- Выделение команд записи.
- HEX-представление переданных параметров.
- Ответ прибора.
- Сравнение обмена до и после операции.
- Возможность сохранить исследованный сценарий для дальнейшего анализа.

После выполнения установки нуля штатным коммуникатором пользователь должен иметь возможность определить, какие команды участвовали в операции.

Учитывать, что процедура может включать несколько последовательных запросов.

Не считать единственную неизвестную команду заведомо командой установки нуля без проверки её назначения.

### 5.5. Перенос выявленных процедур в HART-бро

Если команда и её параметры достоверно установлены:

1. Описать процедуру.
2. Связать её с конкретной моделью и ревизией устройства.
3. Добавить обработку ответов.
4. Реализовать предварительное подтверждение.
5. Проверить процедуру на испытательном датчике.
6. Добавить подтверждённый метод в справочник.

Не выполнять автоматически повтор чужого неизвестного пакета без анализа его структуры и условий применения.

## 6. Взаимодействие с существующим интерфейсом

Не менять ранее согласованную карточку быстрого просмотра.

Сохранить:
- Индикатор состояния слева от названия.
- Производителя и модель.
- TAG в скобках справа от модели.
- Device ID в десятичной форме под моделью.
- Дату производства рядом с номером, уменьшенным шрифтом и без подписи, если она действительно известна.
- Диапазон справа.
- Карандаш слева от диапазона.
- Кнопку «Установить ноль».
- Кнопку «Начать измерительную сессию».

Не добавлять в карточку технические параметры HART-команд.

Информацию о методе установки нуля, кодах ответа и подробностях операции показывать в соответствующем окне и диагностическом журнале.

В режиме обхода датчиков автоматически установку нуля не выполнять.

## 7. Испытания и проверка

### 7.1. Идентификация

Проверить:
1. `0x0026 / 0x2662 / Rev 9` → Метран-150R.
2. Исходный HART Manufacturer ID сохраняется.
3. Неизвестный Device Type не получает выдуманного названия.
4. Модель правильно отображается в карточке и экспорте.
5. Изменения не нарушают идентификацию других Метранов.
6. Результат одинаков через Bluetooth и USB.

### 7.2. Устойчивость обнаружения

Использовать реальные кадры из «ж6».

Проверить:
1. Отсутствие ответа на первую Command 0.
2. Успешное определение со второй попытки.
3. Успешное определение с третьей попытки.
4. Некорректную XOR.
5. Неполный HART-кадр.
6. Ответ с четырьмя байтами FF.
7. Физическую потерю модема.
8. Отсутствие HART-ответов при сохранённом Bluetooth-соединении.
9. Восстановление после кратковременного обрыва.
10. Завершение 60-секундного окна восстановления.
11. Отсутствие конфликтов с периодическим поиском в обходе.

Не принимать повреждённые ответы.

### 7.3. Установка нуля

Проверить:
1. Датчик известной модели.
2. Датчик неизвестной модели.
3. Успешный ответ Command 43.
4. Отказ по неподдерживаемой команде.
5. Защиту записи.
6. Ошибку условий калибровки.
7. Таймаут после отправки команды.
8. Повреждённый ответ.
9. Повторное чтение PV.
10. Регистрацию результата в журнале.
11. Работу через VIATOR.
12. Работу через ЭнИ-406 после подтверждения USB-обмена.

Реальную калибровку выполнять только на подготовленном и разрешённом для настройки датчике.

Не выполнять установку нуля на действующем ответственном технологическом контуре без предусмотренной процедуры вывода прибора на обслуживание.

### 7.4. Прослушивание

Проверить:
- Поддерживается ли пассивный приём у VIATOR.
- Поддерживается ли пассивный приём у ЭнИ-406.
- Отсутствие собственных запросов в режиме прослушивания.
- Корректное определение команд.
- Сохранение HEX.
- Импорт внешнего HEX-журнала, если реализован.
- Возможность определить параметры известной тестовой команды.

Если аппаратная поддержка отсутствует, предоставить подтверждённое ограничение и альтернативный способ анализа.

## 8. Приёмочные критерии

Дополнение считается выполненным, если:

- Метран-150R больше не отображается как неизвестный прибор Rosemount при известной зарегистрированной модели.
- Первоначальная идентификация не прерывается после единственного неудачного запроса.
- Повреждённые кадры отклоняются.
- Причины ошибок HART различаются в журнале.
- Обязательная функция установки нуля реализована.
- Command 43 можно отправить датчику давления без наличия его модели в локальном справочнике.
- Поддержка команды определяется фактическим ответом устройства.
- Результат установки нуля проверяется повторным чтением.
- Команды записи не повторяются автоматически после таймаута.
- Механизм специфических команд расширяем.
- Возможность пассивного прослушивания проверена на уровне оборудования.
- Существующий интерфейс быстрого просмотра сохранён.
- Режим обхода не потерял свою функциональность.
- Обмен через VIATOR и ЭнИ-406 использует общий HART-движок.
