# Техническое задание для Codex
## HART-бро 0.5.2 — переработка интерфейса и поведения приложения

### 1. Общая задача

Внести изменения в существующее Android-приложение **HART-бро 0.5.1**, сохранив текущие реализованные функции обмена с HART-датчиками через Bluetooth-коммуникатор Pepperl+Fuchs VIATOR.

Основная цель обновления — упростить пользовательский интерфейс, улучшить работу с графиком, сделать полноценное диагностическое окно, переработать редактирование параметров и журнал изменений.

**Важно:**

- Не создавать приложение заново.
- Не переписывать работающий транспорт Bluetooth Classic SPP/RFCOMM и HART-протокол без необходимости.
- Сохранить совместимость с существующими записями журнала и настройками.
- Использовать существующие функции чтения, записи, проверки параметров и диагностики там, где они уже реализованы.
- Исключить фиктивные измерения, значения-заглушки и повторное использование PV как SV/TV/QV при отсутствии реальных данных.
- Приоритет — корректность измерений, безопасность записи параметров и устойчивость соединения.

### 2. Верхняя панель приложения

Сейчас в верхней части отображается название «HART-бро 0.5.1», а состояние Bluetooth вынесено в другие элементы интерфейса.

Необходимо сделать компактную постоянную индикацию подключения непосредственно в верхней панели.

**Желаемое представление:**

`HART-бро 0.5.2     [значок BT] VIATOR ✓`

Точное название Bluetooth-устройства брать из фактического подключения. Для длинных названий использовать сокращение с многоточием.

Состояния:

| Состояние | Отображение |
|---|---|
| Bluetooth подключён | Значок Bluetooth и зелёная галочка |
| Переподключение | Значок Bluetooth с индикатором восстановления |
| Bluetooth отключён | Значок Bluetooth и красный крестик |
| Подключено другое устройство | Обновить название и индикатор |

Требования:

1. Индикация должна присутствовать независимо от выбранной вкладки.
2. Состояние и название обновляются при реальных изменениях соединения.
3. Не показывать устаревшее название устройства после переключения на другое.
4. Не занимать чрезмерное пространство, не переносить заголовок приложения на несколько строк без необходимости.
5. Статус Bluetooth не смешивать со статусом обмена HART: работающий Bluetooth не гарантирует ответ датчика.

### 3. Мониторинг — новая структура экрана

Упростить страницу «Монитор».

**Рекомендуемый порядок элементов сверху вниз:**

1. Название обнаруженного HART-датчика и состояние обмена.
2. Кнопка «Открыть диагностику».
3. Текущее значение основного измеряемого параметра.
4. Ток токовой петли датчика.
5. Настройки периодичности опроса, если они уже реализованы.
6. Заголовок «Общий график».
7. График с отображением диапазона датчика.
8. Управление масштабом и просмотром временной шкалы.
9. Управление текущей сессией.

Не загромождать мониторинг служебными кодами, дополнительными динамическими переменными и технической информацией.

#### 3.1. Название датчика и подтверждение HART-обмена

Убрать текст:

«Ответ HART получен».

Вместо него показывать название подключённого датчика и состояние связи.

Примеры:

`Метран-150    ✓`

`Метран-150    ✕`

Название получать из реально прочитанной идентификационной информации. Если определить модель невозможно, показывать нейтральное название «HART-датчик» с доступными идентификационными сведениями.

**Зелёная галочка** означает, что обмен с датчиком стабилен и последнее ожидаемое чтение выполнено успешно.

**Красный крестик** означает потерю обмена или отказ в получении ожидаемых ответов.

Не считать успешный единичный ответ гарантией стабильной связи навсегда. Индикатор должен учитывать актуальные результаты опроса и состояние транспортного канала.

При нарушении связи дополнительно отображать:

- Краткое сообщение о причине нарушения, если она определена.
- Состояние переподключения.
- Оставшееся время попыток восстановления.
- Коды ошибок, если они реально получены.

Пример:

`Метран-150    ✕`

`Переподключение · 42 с`

`Причина: потеря Bluetooth`

Если Bluetooth работает, но датчик не отвечает, показывать именно ошибку HART, не объявляя Bluetooth отключённым.

#### 3.2. Отображение таймаута

Оставшееся время показывать **только в период активных попыток переподключения**.

Размещать время непосредственно рядом с надписью «Переподключение».

Не отображать обратный отсчёт в других частях экрана.

Когда попытки закончились, убрать таймер и показать конечное состояние, например:

`Связь не восстановлена`

Существующий предел переподключения — 60 секунд — сохранить.

Не запускать новый бесконечный цикл попыток после истечения предусмотренного периода без соответствующего пользовательского действия.

#### 3.3. Кнопка «Открыть диагностику»

**Кнопку сохранить.**

Переместить непосредственно под информацию о датчике, в верхнюю часть мониторинга.

При нажатии открывать **диагностическое окно подключённого датчика**.

Запрещено использовать эту кнопку для переключения на вкладку HEX.

Диагностика и HEX — разные функции:

- Диагностика предназначена для просмотра характеристик датчика, состояний, ошибок и редактирования доступных параметров.
- HEX предназначен для технического анализа протокольного обмена.

### 4. Основные измерения мониторинга

Убрать из основного мониторинга длинный список PV, SV, TV, QV с отдельными флажками.

В обычном режиме пользователю нужны только два основных значения:

**1. Измеряемый параметр датчика**

Показывать цифровую основную переменную HART (PV) с единицей измерения.

Пример:

`Перепад давления     −0,00857 кПа`

Для температурного датчика:

`Температура     24,6 °C`

Название параметра определять по типу и конфигурации датчика, если имеются достоверные данные.

**2. Ток датчика**

Показывать фактическое значение тока, прочитанное через HART.

Пример:

`Ток петли     12,34 мА`

Требования:

- Не рассчитывать PV из тока 4–20 мА.
- Не рассчитывать ток из PV вместо фактического чтения.
- Использовать реальные цифровые данные HART.
- Если ток недоступен через поддерживаемые команды, показывать «Нет данных», а не придумывать значение.
- Если показание устарело из-за потери связи, визуально обозначать его как неактуальное.
- Не подставлять значения PV в SV, TV или QV.

Все дополнительные переменные, сведения о процентах диапазона, статусы и служебные параметры перенести в диагностическое окно.

Для двух основных измерений использовать **стабильную одноколоночную компоновку**. Исключить ситуации, когда одни и те же элементы произвольно перестраиваются то в один, то в два столбца.

### 5. Диагностическое окно датчика

По нажатию «Открыть диагностику» показывать отдельный экран или полноценное вложенное окно.

Оно должно включать:

**Информация об устройстве**

- Производитель.
- Модель.
- Device Type.
- HART Revision.
- Идентификатор устройства.
- Версия ПО и другие доступные идентификационные поля.

**Параметры измерения**

- Основная переменная PV.
- Дополнительные переменные, если реально поддерживаются датчиком.
- Ток петли.
- Единицы измерения.
- Нижний и верхний пределы настроенного диапазона.
- Другие доступные параметры.

**Конфигурация**

- Настраиваемые параметры.
- Состояние защиты записи.
- Настройки диапазонов и единиц.
- Другие поддерживаемые параметры.

**Состояние и ошибки**

- Доступные диагностические статусы датчика.
- Коды ошибок и предупреждений.
- Расшифровка статусов, когда она известна.
- Состояние HART-обмена.

#### 5.1. Редактирование параметров

При нажатии на доступный для записи параметр открывать соответствующее окно редактирования.

Если параметр только для чтения, не показывать ложную возможность изменения.

Для любой записи сохранить последовательность:

1. Открыть редактирование.
2. Ввести новое значение.
3. Нажать «Установить».
4. Показать отдельное подтверждение со старым и новым значениями.
5. После подтверждения выполнить HART-запись.
6. Повторно прочитать параметр с датчика.
7. Сравнить результат с запрошенным значением.
8. Отобразить итог проверки и записать его в историю изменений.

Если результат записи неизвестен из-за потери ответа, не повторять запись вслепую: сначала выполнить контрольное чтение.

Не использовать неподдерживаемые команды записи и не предлагать опасные операции без соответствующих предупреждений.

#### 5.2. Убрать лишние сведения

Исправить следующие особенности текущего интерфейса:

- **Device Type** сейчас отображается два раза подряд. Оставить одно корректно подписанное значение. Если строки на самом деле представляют разные поля, дать им разные понятные названия.
- Убрать с этой страницы поле «Дата прочтения данных». Данные должны обновляться при открытии, но дата обновления не нужна в пользовательском представлении.
- В строке состояния защиты записи убрать фразу «по данным команды 15». Оставить только понятное состояние, например «Защита записи: отключена».
- Убрать из обычного представления необработанную переменную `0x40`. Не показывать её как самостоятельный интересующий пользователя параметр.

При необходимости исходные байты и протокольные сведения сохранять во вкладке HEX. Значимые диагностические состояния представлять текстом, а не просто шестнадцатеричным кодом.

### 6. Редактирование диапазона и единиц измерения

Переработать существующее окно установки нижней и верхней границ диапазона.

#### 6.1. Замена старого значения при вводе

При открытии окна показывать текущие значения.

Когда пользователь начинает вводить новое значение, старое значение должно заменяться **с первого введённого символа**.

Практически:

- При переходе в поле выделять всё текущее числовое значение.
- Первое введение цифры, минуса, десятичного разделителя или вставка нового числа заменяет выделенное.
- Не требовать ручного удаления старых цифр.
- При повторном редактировании уже введённого значения позволять обычное позиционирование курсора и исправление.
- Не стирать значение просто при открытии окна, без фактического ввода.

Обеспечить корректную работу отрицательных значений и дробных чисел.

#### 6.2. Расположение элементов

Нижний и верхний пределы расположить в одной строке с разделителем «—».

Справа расположить выпадающий список единиц измерения.

Условный вид:

`[ 0 ] — [ 16 ]    [ кПа ▾ ]`

При открытии окна в списке должна быть выбрана **текущая единица измерения датчика**.

Список должен включать только единицы, поддерживаемые фактической HART-функциональностью данного устройства для этого параметра.

Не предлагать произвольные единицы, которые прибор не способен принять.

#### 6.3. Совместное изменение диапазона и единиц

Пользователь должен иметь возможность в одной операции указать:

- Нижнюю границу.
- Верхнюю границу.
- Единицу измерения.

При переключении единицы необходимо корректно обрабатывать физический смысл диапазона.

Например, переход с `0—16 кПа` на `0—0,016 МПа` должен сохранять те же физические пределы, если пользователь отдельно их не изменил.

Использовать правильные преобразования, включая смещения для температурных шкал, если соответствующие единицы доступны.

Изменение единицы в интерфейсе не должно автоматически означать изменение физических уставок без ведома пользователя.

Перед записью показать все запланированные изменения и подтвердить их.

Фактические HART-команды и порядок записи определять по поддерживаемым возможностям датчика. Не считать, что все модели одинаково поддерживают запись диапазона и единиц.

После выполнения обязательно перечитать фактические границы и единицу измерения.

Если часть операции не поддерживается или не подтверждена, отобразить это явно, без ложного сообщения об общем успехе.

### 7. Размещение диапазона на графике

На предоставленном скриншоте оранжевым обведено желаемое место для отображения диапазона датчика.

**Разместить диапазон в правой верхней части области графика, непосредственно над построением, в отмеченном пользователем месте.**

Пример отображения:

`0—16 кПа`

Не размещать этот диапазон посреди легенды переменных и не дублировать его в нескольких местах мониторинга.

При изменении диапазона или единицы измерения данные должны обновляться.

**Важно различать:**

- Диапазон датчика — реально настроенные нижняя и верхняя границы измерения.
- Масштаб графика по вертикали — визуальный диапазон отображения текущих измерений.

Это разные сущности.

Например, датчик может иметь диапазон `0—16 кПа`, а график текущих колебаний — отображать участок от `−0,0092` до `−0,0084 кПа`.

Изменение масштаба графика не должно менять настройки датчика.

Если диапазон датчика не удалось достоверно прочитать, показывать «Диапазон недоступен», не подставляя пределы вертикальной оси графика.

### 8. Общий график и временная шкала

Исправить поведение графика. Сейчас перемещение по истории и автоматическое следование работают непоследовательно.

#### 8.1. Стандартный временной масштаб

Установить начальный стандартный масштаб **60 секунд видимой истории**.

Это значение использовать по умолчанию при открытии нового мониторинга, если пользователь не выбрал другой масштаб в текущей сессии.

Масштаб времени не должен самопроизвольно расширяться по мере увеличения длительности записи.

При продолжительной работе новые точки появляются справа, а старые уходят за левую границу видимой области.

**Важно:** старые точки должны исчезать только из текущего видимого окна, но сохраняться в данных активной сессии для последующего просмотра и сохранения.

#### 8.2. Автоматическое следование

По умолчанию режим «Следовать» включён.

Пока пользователь не вмешивается:

- Правый край графика соответствует актуальному времени.
- Новые данные добавляются справа.
- Временное окно сохраняет заданную ширину.
- Старые данные плавно уходят влево.

При ручном перемещении графика в прошлое автоматическое следование выключается.

Пользователь может свободно просматривать ранее полученные измерения.

#### 8.3. Возвращение к текущему времени

**При ручной перемотке графика обратно к настоящему времени автоматическое следование включается самостоятельно.**

Не требовать обязательного нажатия кнопки «Следовать».

Для определения достижения текущего времени использовать разумную небольшую погрешность, связанную с фактическим интервалом опроса, чтобы исключить необходимость попадать пальцем в точный пиксель.

Если пользователь прокручивает шкалу до правого края актуальных данных:

1. Включить режим следования.
2. Обновить состояние кнопки «Следовать».
3. Продолжить автоматическое смещение временного окна вместе с поступлением новых точек.

#### 8.4. Сохранение масштаба при перемотке

Если отображается 60-секундный участок, ручное перемещение по истории должно передвигать именно 60-секундное окно.

Не изменять длительность окна автоматически.

Изменение временного масштаба разрешается только при явном действии пользователя:

- «Масштаб +».
- «Масштаб −».

Масштабирование должно менять длительность отображаемого интервала, а не частоту опроса датчика.

При просмотре истории масштабировать относительно просматриваемого участка, не перебрасывая пользователя без необходимости к настоящему времени.

При включённом следовании правый край остаётся привязанным к актуальным данным.

#### 8.5. Кнопка «Следовать»

Кнопку оставить.

Она позволяет быстро вернуться из истории к текущим данным.

Если следование уже включено, отображать это состоянием кнопки.

Не допускать рассинхронизации, когда кнопка показывает активное следование, а график остаётся в прошлом.

#### 8.6. Отображение измерений на графике

Основной мониторинг показывает только основной измеряемый параметр и ток петли.

По умолчанию график строится для основного параметра.

Если реализовано включение тока на графике, он должен отображаться на том же временном графике, но с отдельной вертикальной шкалой в мА.

Не смешивать разные физические единицы на одной числовой шкале.

Не выводить четыре почти совпадающие линии PV/SV/TV/QV только ради заполнения интерфейса.

В диагностике дополнительные переменные остаются доступными независимо от того, показаны ли они на основном графике.

#### 8.7. Пропуски обмена

Сохранить корректное отображение нарушений связи:

- Нет ответа — нет новой измерительной точки.
- В период отсутствия данных линия прерывается.
- После восстановления обмена линия продолжается с новой точки без соединения через пропущенный интервал.
- Не интерполировать пропущенные измерения.
- Хранить реальные метки времени чтения.

При выходе из паузы или после восстановления связи не изменять произвольно выбранный пользователем временной масштаб.

### 9. Журнал изменений параметров

Переработать журнал истории изменения конфигурации.

Текущий вариант занимает слишком много пространства.

Сделать компактные записи с тремя основными областями:

**Слева:** дата и время изменения.

**В центре:** перечень изменённых параметров.

**Справа:** результат проверки.

Пример:

`01.11 16:45    Нижний предел: 0 → 2 кПа       ✓`
`               Верхний предел: 16 → 20 кПа`
`               Единица: кПа → МПа`

Это пример визуальной структуры, а не пример допустимого физического преобразования значений.

Требования:

1. Одна операция изменения конфигурации — одна запись журнала.
2. Если в одной операции изменено несколько параметров, каждый выводить в отдельной строке внутри записи.
3. Не повторять дату для каждого параметра одной операции.
4. Для успешно выполненной и подтверждённой операции показывать зелёную галочку.
5. Для неудачной операции или отрицательного результата контрольного чтения показывать красный крестик.
6. Если результат неизвестен или частично подтверждён, использовать отдельный нейтральный/предупреждающий статус, не выдавая его за успех.
7. При нажатии на запись можно открыть подробности: прежние и новые значения, фактический ответ датчика, ошибки и результаты проверки.
8. Не загромождать компактную строку техническими деталями HART.
9. Использовать понятные обозначения статусов, доступные не только по цвету.

#### 9.1. Удаление записей

Добавить возможность:

- Удалить отдельную запись истории.
- Удалить все записи истории после подтверждения.

Разместить управление удалением компактно, например в контекстном меню записи.

Удаление истории из приложения не должно вызывать никаких HART-команд и не должно изменять конфигурацию датчика.

#### 9.2. Разделение журналов

Не смешивать два разных типа данных:

**История изменений конфигурации** — сведения о выполненных операциях записи и их проверке.

**Сохранённые сессии мониторинга** — временные ряды измерений и отчёты, которые пользователь сохраняет вручную.

Сохранить существующий принцип: измерительная сессия не записывается в постоянный журнал автоматически без команды пользователя «Сохранить сессию».

Для сохранённых сессий также должна остаться возможность отдельного удаления.

### 10. Очистка остальных служебных надписей

Убрать лишнюю техническую информацию с основных пользовательских экранов.

В частности:

- Не показывать необработанный статус `0x40` на странице мониторинга и в обычной карточке датчика.
- Не дублировать Device Type.
- Не выводить «по данным команды 15» рядом с защитой записи.
- Не показывать дату чтения данных на странице диагностики.
- Не дублировать уведомление об успешном HART-ответе, если его уже заменяет индикатор состояния.
- Не повторять Bluetooth-статус крупными текстовыми блоками, если информация уже представлена в заголовке. При ошибках подробное пояснение допустимо и необходимо.

Исходные протокольные сведения не удалять из приложения полностью. Они должны оставаться доступны в HEX и, когда действительно нужны для устранения ошибки, в соответствующем диагностическом разделе.

### 13. Проверки перед выпуском APK

Выполнить доступные автоматизированные проверки, а также предусмотреть следующие сценарии испытаний.

**Сценарий 1 — мониторинг**

- Подключён VIATOR.
- Прочитано название HART-датчика.
- В верхней панели показаны Bluetooth-устройство и его актуальный статус.
- В мониторинге показаны только основной параметр и ток.
- Индикация успешного HART-обмена зелёная.
- Диапазон отображается в отмеченном месте справа над графиком.
- Кнопка диагностики открывает диагностику, а не HEX.

**Сценарий 2 — график**

- Начальная длительность временного окна — 60 секунд.
- При поступлении новых точек график следует за текущим временем.
- По истечении 60 секунд видимая область не расширяется автоматически.
- Ручное движение в прошлое отключает следование.
- При прокрутке сохраняется установленный масштаб.
- Ручное возвращение к настоящему времени снова включает следование.
- Кнопка «Следовать» возвращает график к актуальным данным.
- Масштаб +/− работает независимо от периодичности HART-опроса.
- История за пределами видимой области остаётся доступна.
- При потере обмена отсутствующий интервал не соединяется искусственной линией.

**Сценарий 3 — диагностика**

- Показан один корректный Device Type.
- Отсутствует ненужная дата прочтения.
- Состояние защиты записи не содержит фразы «по данным команды 15».
- Необработанное `0x40` не отображается как отдельный пользовательский параметр.
- Доступны дополнительные параметры датчика.
- При нажатии на редактируемый параметр открывается правильное окно.
- Недоступные для записи параметры не предлагают выполнение записи.

**Сценарий 4 — диапазон**

- Окно показывает действующие границы и текущую единицу.
- Первое введение нового символа заменяет старое числовое значение.
- Границы расположены в одной строке.
- Список единиц расположен справа.
- Переключение единиц корректно преобразует значения.
- Неподдерживаемые единицы не предлагаются.
- Перед записью требуется отдельное подтверждение.
- После записи выполняется контрольное чтение.
- В случае неподтверждённого результата не показывается ложный успех.

**Сценарий 5 — журнал**

- Одна операция отображается компактной записью.
- Несколько изменений выводятся отдельными строками.
- Справа показывается значок результата проверки.
- Можно открыть подробности.
- Можно удалить отдельную запись.
- Можно удалить всю историю после подтверждения.
- Удаление не приводит к HART-записи.
- Старые записи сохраняются после обновления APK.

**Сценарий 6 — потеря связи**

- При потере Bluetooth изменяется значок в верхней панели.
- При потере HART-ответов изменяется индикатор датчика.
- Неисправность HART не маскируется под потерю Bluetooth.
- Таймер появляется только во время попыток переподключения.
- Время находится рядом с надписью «Переподключение».
- После истечения 60 секунд таймер исчезает.
- Возобновление связи не создаёт фиктивные точки на графике.
- Подключение к другому датчику не объединяет его измерения с предыдущей сессией.

### 14. Требования к реализации и результату

Работать с существующим репозиторием и архитектурой приложения.

Перед изменениями определить, какие функции уже существуют, чтобы не дублировать их и не нарушить работающие механизмы.

Для графика отдельно хранить:

- Измерительные данные текущей сессии.
- Текущее временное окно просмотра.
- Выбранный временной масштаб.
- Состояние автоматического следования.

Для состояния интерфейса отдельно учитывать:

- Состояние Bluetooth.
- Состояние HART-обмена.
- Идентификатор активного датчика.
- Актуальность последних измерений.
- Состояние операции записи и её проверки.

Для редактирования диапазона не смешивать изменение чисел в форме, преобразование единиц и реальную отправку конфигурации в прибор.

**Не выполнять реальных HART-команд записи ради автоматизированных тестов на неизвестном или работающем технологическом оборудовании.** Использовать тестовые данные, имитацию ответов или отдельную безопасную испытательную среду.

По завершении:

1. Обновить отображаемую версию приложения до **0.5.2**.
2. Собрать устанавливаемый APK для испытаний.
3. Выполнить доступные тесты и сборку.
4. Указать, какие проверки реально выполнены, а какие требуют подключения физического датчика.
5. Кратко перечислить внесённые изменения.
6. Сообщить об ограничениях, особенно если конкретный HART-датчик не поддерживает изменение единиц или некоторые команды чтения и записи.

**Ожидаемый результат:** компактный и понятный мониторинг с правильно работающим графиком, отдельной полноценной диагностикой, удобным редактированием диапазона и единиц, компактной историей изменений и информативной индикацией Bluetooth/HART без лишней технической информации на основном экране.
