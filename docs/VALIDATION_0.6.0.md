# Проверки HART-бро 0.6.0

Ветка `feature/0.6.0-usb-walk`, база 0.5.3 `38ea403`; включено [дополнение](SUPPLEMENT_0.6.0.md). Локальные проверки выполнены; полный Android CI ещё не завершён. Физического ЭнИ-406 и стенда нуля/пассивного приёма нет, аппаратная приёмка не заявляется.

## Измерение обхода до/после

Один и тот же `WalkTiming060Test.kt` выполнен на исходниках 0.5.3 и 0.6.0. Корутинные виртуальные часы: задержка каждого имеющегося ответа 150 мс, timeout 1500 мс, HART 7, используемый длинный TAG. Это проверка программного расписания, а не измерение скорости телефона/модема/перестановки щупов.

| Сценарий | 0.5.3 | 0.6.0 |
|---|---:|---:|
| Идентификация доступного датчика | 150 мс | 150 мс |
| Только конфигурация, все ответы | 600 мс: 20,15,14,16 | 450 мс: 13,15,20 |
| Только конфигурация, молчат ненужные 14/16 | 3500 мс, 2 таймаута | 450 мс, 0 таймаутов |
| Фактический период TX №0 без датчика | 2700 мс | 2100 мс |
| Timeout №0 | 1500 мс | 1500 мс |

Период TX включает timeout, паузу после завершения и прежние 200 мс тишины после неуспешного чтения. В исходниках 0.5.3 пауза была 1000 мс, в новом коде — 400 мс. Упомянутые в ТЗ 1200 мс не подставлялись вместо измеренного поведения исходной версии. При успешном ID дополнительной паузы перед конфигурацией нет. Медленные ответы за 1400 мс отдельно проходят при прежнем timeout 1500 мс, включая сценарии отсутствующих 13/15 и ограниченного повтора. Основной HART 5 маршрут проверяется отдельно как 0→13→15; для HART 6/7 добавляется реально используемый 20.

Полный полевой обход пользователя (12 строк около 4:43) не сравнивался с виртуальным тестом: он включает ручное переключение. Задержка обнаружения после появления ответа, реальное время конфигурации, время экспорта на телефоне и накладные расходы должны быть измерены повторным полевым логом. В APK есть PERF для этих этапов, длительности/исходы команд, bounded retry, строки/совпадения ID и XLSX.

## Локальные проверки

JDK 21 / Gradle 8.13 / Android SDK 36. Команда:

```sh
./gradlew :hart-core:test :transport-usb:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug --offline --no-daemon -Pkotlin.compiler.execution.strategy=in-process
./gradlew :hart-core:walkExampleReview -PwalkReviewDir=/tmp/hart-walk-review
python3 tools/validate_walk_xlsx.py /tmp/hart-walk-review
```

Окончательная локальная сборка успешна: **247 core JVM + 18 USB JVM = 265 тестов, 0 failures/errors/skipped**. APK и инструментальный APK собраны, lint — 0 ошибок, 2 предупреждения: NewerVersionAvailable и рекомендация UseKtx. Независимый openpyxl сравнил все 505 ячеек контрольной 100-строчной ведомости, пять колонок, десятичные ID и точность дат. Полный CI для дополнения будет указан после завершения Android-регрессии.

Проверяются permission grant/deny/dismiss, поздний grant после отключения, отсутствие повторного permission-цикла, распознавание только upstream FTDI/WCH VID/PID, открытие scripted-порта/close/read/write errors/detach/reattach, fragments/4FF/нет XOR/поздний XOR, повтор на открытом порту, отмена/однократность 35, разделение статуса HART и транспорта. Политика разрешений и scripted SerialPortIo проверяют программную логику, не системный USB-контроллер и не настоящие диалоги телефона.

Android-набор сохраняет все 28 прежних сценариев и добавляет три USB-сценария: настоящий пустой UsbManager inventory без фиктивного порта/Activity recreate; HART timeout с открытым соединением и повтором; индикатор отключения и восстановление без запуска сессии. USB/HART-соединение этих двух последних тестов подменяется connectionFactory. Прежние три пятиминутных фоновых периода и проверки однократной записи сохранены. Ещё четыре Android-сценария проверяют Метран-150R и исходную диагностику, ноль неизвестной модели с двумя шагами и recreate, импорт/сохранение HEX без подключения и приём foreground без TX после recreate. Ожидаемый полный набор — 35 Android-тестов; предварительный UI-набор — 19.

## Аппаратная проверка

Ни реальные VID/PID пользовательского ЭнИ-406, ни UART baud/parity/RTS/DTR, ни успешный HART-обмен через физический модем здесь не подтверждены. Нет испытания установки поверх телефона пользователя. Драйверы FTDI и WCH CH34x включены по таблицам USB Serial 3.11.0, без произвольного VID/PID mapping; поддержка контроллера не сертифицирует ревизию ЭнИ.

## Регрессия по реальному журналу и нулю

Из «ж6 не нашел датчик.txt» сохранены только три исходных кадра с UTC (без Bluetooth-адреса телефона): неполный 01:33:58, неверный XOR 04:34:42 и корректный 4 FF 04:34:49 от 03.11.2026. Тесты отклоняют первые два, принимают третий как 0x0026/0x2662/Rev 9 и не изменяют исходное имя производителя Rosemount. Другие ревизии не получают имя Метран-150R автоматически.

Новые JVM-сценарии проверяют успех на второй/третьей начальной попытке и ограниченную ошибку после трёх, причины ошибок и сохранение транспорта, 43 для неизвестной модели (пустой data/актуальный адрес/одна передача), коды отказа, потерянный/повреждённый ACK, принятую, но непроверенную операцию, контроль допусков, точный профиль 52 и чтение старого журнала. Отдельные USB-тесты прогоняют полный ноль и потерю ACK через настоящий `UsbHartTransport` со scripted native port, а также закрытие порта при native write timeout без повтора 35. Тесты анализа проверяют запрет TX, время фрагментов, XOR, импорт/сравнение/неоднозначность и остановку с неполным кадром. Это программный обмен, не испытание физического модема.
