# ЧАСТЬ I. СОСТОЯНИЕ СУЩЕСТВУЮЩЕГО ПРОЕКТА

## 1. Назначение приложения

HART-бро — автономный HART-коммуникатор для Android.

Основные задачи конечного приложения:

- Чтение цифровых измерений.
- Получение полной доступной конфигурации прибора.
- Изменение поддерживаемых параметров.
- Диагностика датчиков.
- Мониторинг измеряемых переменных с графиками.
- Сохранение проверок по запросу пользователя.
- Экспорт измерений и отчётов.
- Копирование конфигурации между приборами.
- Исследование низкоуровневого HART-обмена.
- Поддержка дополнительных моделей датчиков через расширяемые профили.

На первом этапе испытаний используем датчики давления и температуры.

В будущем список поддерживаемых типов оборудования будет расширяться.

Приложение предназначено для инженерного использования. Приоритеты — достоверность измерений, корректность протокола, удобство эксплуатации и безопасность операций записи.

## 5. Испытательное оборудование

Pepperl+Fuchs VIATOR Bluetooth HART Interface.

Модель: `HM-MT-BT-EX-010041`.

Обнаруженное устройство:

`MACTekViator3B1F`

Интерфейс:

Bluetooth Classic SPP.

**Телефон:**

Android 16, API 36.

**Испытанный датчик:**

Метран-150, датчик перепада давления.

Данные прибора:

- Производство: 07.2025.
- Верхний предел перепада: 40 кПа.
- Допустимое статическое давление: 25 МПа.
- HART Revision: 7.
- Manufacturer: `0x0099` — Метран.
- Expanded Device Type: `0x9972`.
- Device ID: `5FCA7F`.
- Software Revision: 40.
- Device Revision: 7.

Во время испытания перепад давления был фактически нулевым.

Полученное HART-показание совпало с показанием штатного экрана датчика.

Это подтверждённый результат испытания версии 0.1.1, а не результат симуляции.

## 6. Контрольные HART-кадры

Использовать следующие данные для регрессионных тестов.

### 6.1. Запрос команды 0

20 преамбул `FF`.

```text
FF FF FF FF FF FF FF FF FF FF
FF FF FF FF FF FF FF FF FF FF
02 80 00 00 82
```

### 6.2. Реальный ответ команды 0

```text
FF FF FF FF
06 80 00 18 00 20
FE 99 72 05 07 07 28 08
00 5F CA 7F 05 09 00 2C
00 00 99 00 99 01 45
```

Ожидаемые характеристики:

- 4 принятые преамбулы.
- Разделитель `0x06`.
- Команда 0.
- Byte Count `0x18`.
- Response Code `0x00`.
- Device Status `0x20` — Cold Start.
- Checksum `0x45`, корректна.
- Производитель Метран.
- HART 7.
- Expanded Device Type `0x9972`.
- Device ID `5FCA7F`.

Статус Cold Start не означает изменение конфигурации приложением.

Для ранее зафиксированного ответа того же формата со статусом `0x00` контрольная сумма была `0x65`. Оба варианта можно использовать в тестах.

### 6.3. Запрос команды 1

```text
FF FF FF FF FF FF FF FF FF FF
FF FF FF FF FF FF FF FF FF FF
82 99 72 5F CA 7F 01 00 82
```

### 6.4. Реальный ответ команды 1

```text
FF FF FF FF
86 99 72 5F CA 7F
01 07 00 00
0C BC 59 F8 6F
FF
```

Ожидаемые значения:

- Разделитель `0x86`.
- Команда 1.
- Byte Count `0x07`.
- Response Code `0x00`.
- Device Status `0x00`.
- Unit Code `0x0C` — кПа.
- Float32 `BC 59 F8 6F`.
- PV приблизительно `−0.01330386 кПа`.
- Checksum `0xFF`, корректна.

При отображении допустимо округлять до удобного количества знаков. Исходное число сохранять без искусственного преобразования.

### 6.5. Особенности приёма

Реальные ответы VIATOR поступают фрагментами размером приблизительно 1–4 байта.

Обязательно сохранять накопительный потоковый парсер, поскольку RFCOMM не гарантирует соответствия фрагментов отдельным HART-кадрам.

Нельзя возвращаться к ошибке версии 0.1.0, когда после получения `FF FF FF FF 06` приложение отвергало корректный ответ.

# ЧАСТЬ III. ОБЩИЕ ПРИНЦИПЫ АРХИТЕКТУРЫ

## 8. Транспортная независимость

Сохранить разделение между HART-движком и транспортом.

Архитектура должна поддерживать абстракцию:

`HartTransport`

Текущая реализация:

`BluetoothSppTransport`

Будущая реализация:

`UsbSerialTransport`

Не разрабатывать USB-транспорт в версии 0.2.0.

Не создавать отдельные HART-движки для разных модемов.

## 9. Очередь HART-команд

Для каждого активного подключения должна существовать единственная последовательная очередь запросов.

Требования:

- Не отправлять конкурирующие запросы одновременно.
- Сопоставлять ответ с ожидаемой командой и адресом.
- Проверять контрольную сумму.
- Различать неподдерживаемую команду, ошибку ответа и таймаут.
- Корректно обрабатывать отмену.
- Не принимать устаревшие данные за новое измерение.
- Не блокировать Android UI.
- Не создавать очередь измерений, если реальный HART-обмен медленнее заданного периода опроса.

Не применять автоматические повторы команд изменения конфигурации.

## 10. Универсальная модель измерений

Создать независимую от конкретного датчика модель измеряемой переменной.

Каждая переменная должна содержать:

- Код или идентификатор.
- Назначение, если известно.
- Человекочитаемое название.
- Исходное цифровое значение.
- Единицу измерения.
- Исходный код единицы HART.
- Статус качества.
- Временную метку получения.
- Команду HART, из которой получено значение.

Должна поддерживаться ситуация, когда прибор отдаёт только PV либо несколько дополнительных переменных.

Не привязывать внутреннюю архитектуру исключительно к давлению и температуре.

При неизвестном назначении переменной использовать техническое обозначение, не угадывая физический смысл.

# ЧАСТЬ IV. ТЕКУЩЕЕ ЗАДАНИЕ: ВЕРСИЯ 0.2.0

## 11. Основная цель

Разработать полноценный режим непрерывного мониторинга цифровых HART-измерений.

Обязательные функции:

1. Чтение всех поддерживаемых динамических переменных.
2. Периодический опрос.
3. Единый график измерений.
4. Управление активной сессией.
5. Работа при свёрнутом приложении.
6. Контроль потери связи.
7. Автоматическое восстановление в течение 60 секунд.
8. Сохранение разрывов на графике.
9. Минимальное ручное сохранение сессий.
10. Просмотр и удаление сохранённых сессий.

**Версия 0.2.0 остаётся полностью в режиме чтения.**

Никаких команд записи в реальные датчики в этой версии.

## 12. HART-команды для нового этапа

Развить существующий HART-клиент.

Необходимые команды:

| Команда | Назначение |
|---|---|
| 0 | Read Unique Identifier |
| 1 | Read Primary Variable |
| 3 | Read Dynamic Variables and Loop Current |
| 8 | Read Dynamic Variable Classifications |
| 9 | Read Device Variables with Status |
| 48 | Read Additional Device Status |
| 50 | Read Dynamic Variable Assignments |

Команды 0 и 1 уже реализованы.

Для новых команд использовать корректные структуры запросов и ответов согласно поддерживаемой ревизии HART.

Команда №9 должна содержать запрошенные коды переменных. Для динамических PV, SV, TV, QV в HART 7 учитывать предусмотренные стандартом коды 246–249.

Проверить форматы и ограничения каждой команды по документации, а не строить их по предположению.

Не все датчики обязаны поддерживать все необязательные команды.

При ответе «команда не поддерживается»:

- Зафиксировать результат.
- Отключить этот способ чтения для текущей сессии.
- Перейти к другому поддерживаемому способу.
- Не объявлять весь прибор неисправным.

Команды расширенной диагностики не нужно циклически выполнять вместе с каждым измерением.

## 13. Первоначальное определение переменных

После подключения к VIATOR и HART-идентификации:

1. Прочитать PV.
2. Получить доступные динамические переменные.
3. Определить единицы.
4. Определить назначение переменных, если прибор позволяет.
5. Определить статусы их достоверности.
6. Сформировать список доступных параметров.
7. Перейти к мониторингу.

На нашем Метране-150 ожидается как минимум PV перепада давления.

Дополнительные величины пока неизвестны.

Не записывать в код жёсткое утверждение, что SV обязательно является температурой сенсора или что TV является статическим давлением.

Прибор может иметь собственные назначения переменных.

### Источник цифровых измерений

Это принципиальное требование пользователя.

**Все измеряемые величины получать непосредственно из цифровых HART-данных датчика.**

Не рассчитывать давление, температуру или другие величины из тока 4–20 мА.

Токовый выход, сообщаемый датчиком, показывать отдельно как диагностический параметр.

Не считать его независимым физическим измерением тока мультиметром.

## 14. Периодический опрос

Создать Measurement Engine.

Опрос начинается после подключения и перехода в режим мониторинга.

Пользователь может приостановить и возобновить его.

Предусмотреть интервалы:

- 1 секунда.
- 2 секунды.
- 5 секунд.
- 10 секунд.

По умолчанию — 2 секунды.

Интервал является целевым. Если HART-обмен выполняется дольше, следующая операция начинается после завершения предыдущей.

Не накапливать просроченные запросы.

По возможности получать несколько значений одной HART-командой.

Не выполнять несколько отдельных запросов без необходимости, если поддерживаемая команда может вернуть нужные переменные одновременно.

Реальное время ответа показывать в диагностике.

Не генерировать искусственные промежуточные значения.

## 15. Главный экран мониторинга

Сохранить существующий визуальный стиль приложения, постепенно развивая его.

Предлагаемая структура:

### Верхняя панель

- Название HART-бро.
- Статус Bluetooth.
- Статус HART.
- Название или идентификатор датчика.
- Продолжительность сессии.

### Область измерений

- Основной измеряемый параметр крупным шрифтом.
- Единица измерения.
- Другие доступные переменные.
- Статусы измерений.

### График

Один общий график всех выбранных измеряемых величин.

### Управление

- Приостановить.
- Продолжить.
- Сохранить сессию.
- Завершить сессию.
- Открыть диагностику.

Не допускать обрезания текста и наложения кнопок.

Поддерживать светлую и тёмную темы.

## 16. Единый график измерений

**График должен быть общим. Разделять измеряемые параметры на отдельные графики нельзя.**

Требования:

- Одна временная ось X.
- Несколько линий измерений.
- Отдельный цвет для каждого параметра.
- Легенда.
- Возможность включать и отключать отдельные линии.
- Масштабирование.
- Перемещение по времени.
- Автоматическое следование за новыми измерениями.
- Просмотр значения и времени отдельной точки.

У разных физических величин могут быть разные шкалы Y.

Предусмотреть независимые масштабы, сохраняя один общий график. Если одновременно отображается много переменных, интерфейс должен оставаться читаемым.

В подписях и подробностях точек всегда показывать реальные значения и единицы.

### Недостоверные и отсутствующие данные

Если датчик перестал отвечать, значение недостоверно или опрос приостановлен:

- Не подставлять нулевые значения.
- Не повторять последнее измерение как новое.
- Не соединять соседние точки через неизвестный интервал.
- Не использовать интерполяцию.
- Показывать временной разрыв линии.

После восстановления измерений продолжать линию с нового сегмента.

Эти разрывы должны сохраняться в архиве сессии.

## 17. Управление сессиями

Ввести Session Manager.

Одна сессия относится к одному конкретному HART-устройству.

При начале сессии фиксировать:

- Время начала.
- Bluetooth-коммуникатор.
- HART ID датчика.
- Производителя.
- Доступные идентификационные данные.
- Измеряемые переменные.

Во время работы накапливать:

- Измерения.
- Временные метки.
- Качество значений.
- Интервалы потери связи.
- События восстановления.

Данные активной сессии сохраняются во временном рабочем хранилище, не попадая автоматически в постоянный журнал.

Для длительных сессий не хранить неограниченные массивы исключительно в Compose-состоянии.

Использовать эффективный временный буфер или внутреннее временное хранилище с контролем объёма.

### Ручное сохранение

Добавить кнопку **«Сохранить сессию»**.

При нажатии:

1. Зафиксировать снимок накопленной истории до текущего момента.
2. Сохранить данные измерений.
3. Сохранить сведения о датчике.
4. Сохранить временные интервалы потери связи.
5. Подтвердить успешное сохранение.

Сохранение не обязано завершать текущую сессию.

Повторное сохранение по запросу пользователя разрешено.

После завершения без сохранения временные данные удаляются, но ранее сохранённые снимки не затрагиваются.

## 18. Минимальный журнал версии 0.2.0

Полноценный журнал с фильтрами, сравнением конфигураций и экспортом будет реализован позднее.

Но версия 0.2.0 уже должна поддерживать:

- Постоянное локальное хранение вручную сохранённых сессий.
- Список сохранённых проверок.
- Открытие проверки.
- Просмотр графика.
- Удаление записи.
- Подтверждение удаления.

Можно использовать Room.

**Никакого автоматического сохранения сессий.**

Сохранение технических логов также выполняется только по запросу пользователя.

Если полноценный механизм архивирования ещё не готов, не создавать декоративную кнопку «Сохранить», которая не выполняет действие.

## 19. Потеря связи

Различать:

1. Потерю Bluetooth.
2. Отсутствие HART-ответов при исправном Bluetooth.
3. Недостоверные измеряемые переменные.
4. Отдельные ошибочные кадры.

Единичная ошибка HART не должна немедленно восприниматься как окончательная потеря связи.

Реализовать критерий подтверждённой потери обмена на основании последовательных ошибок или обнаруженного физического отключения.

При подтверждённой потере связи:

1. Остановить нормальный опрос.
2. Запомнить время потери.
3. Прервать линии графика.
4. Показать статус «Связь потеряна».
5. Начать восстановление.
6. Запустить общий таймаут 60 секунд.

Не продолжать отображать последнее значение как актуальное без соответствующего обозначения.

## 20. Автоматическое восстановление

### Если Bluetooth подключён, но HART не отвечает

Не разрывать Bluetooth без необходимости.

Попробовать восстановить корректный HART-обмен безопасными командами чтения.

### Если Bluetooth отключился

Попытаться восстановить RFCOMM-соединение с ранее выбранным коммуникатором.

После восстановления снова идентифицировать HART-датчик.

### Общее поведение

- Таймаут всего процесса восстановления — 60 секунд.
- Без конкурирующих подключений.
- Без автоматических команд записи.
- Без нового подтверждения подключения, если восстановление происходит в рамках уже подтверждённой сессии к тому же коммуникатору.
- С проверкой уникального HART ID после восстановления.
- С использованием монотонного времени для отсчёта таймаута.

Если найден тот же датчик, продолжить прежнюю сессию.

Если обнаружен другой датчик, автоматически объединять данные нельзя.

Пользователю необходимо предложить завершить или сохранить старую сессию и затем начать новую.

## 21. Таймаут восстановления

Если в течение 60 секунд связь не восстановлена, прекратить попытки и показать окно:

**«Связь не восстановлена»**

Сообщение:

«Не удалось восстановить связь с датчиком в течение 60 секунд. Что сделать с текущей сессией?»

Две кнопки:

- **Сохранить сессию**
- **Завершить без сохранения**

При сохранении записать полученные до потери данные, включая интервал отсутствия связи, и завершить сессию.

При завершении без сохранения удалить временную историю этой сессии.

Не выполнять ни одно действие автоматически.

Если приложение свёрнуто, показать системное уведомление о необходимости решения. Не пытаться принудительно открыть окно поверх других приложений в обход ограничений Android.

## 22. Работа в фоне

При сворачивании HART-бро или блокировке экрана мониторинг должен продолжаться в рамках разрешённого Android режима.

Использовать подходящий foreground service, в частности тип `connectedDevice`, с корректными разрешениями и системным уведомлением.

Службу запускать при разрешённом системой пользовательском действии.

После завершения сессии:

- Остановить опрос.
- Закрыть Bluetooth-соединение.
- Освободить ресурсы.
- Завершить foreground service.

Не создавать бессрочно работающий скрытый процесс.

Корректно учитывать системные ограничения Android 10–16, включая возможное прекращение процесса операционной системой.

Не обещать восстановление связи после принудительного завершения приложения, если это не гарантируется Android.

## 23. Диагностика

3. Приложение показывает старое и новое значения.
4. Появляется запрос «Вы уверены?».
5. Пользователь нажимает «Да».
6. Приложение отправляет соответствующую HART-команду.
7. После записи повторно считывает параметр.
8. Проверяет фактический результат.
9. Показывает успех, ошибку или неопределённый результат.

9. Получить явное подтверждение.
10. Выполнить разрешённые записи с последующей проверкой результата.

Шаблоны должны храниться **отдельно от журнала проверок**.

- Какие проверки допускаются только на лабораторном стенде.

Не дробить одно испытание на множество запросов, требующих повторного доступа к прибору.

### План первого испытания 0.2.0

**Проверка 1. Подключение**

Подключиться через VIATOR после подтверждения.

Проверить идентификацию Метрана-150.

**Проверка 2. Измеряемые переменные**

Прочитать доступные PV/SV/TV/QV.

Сохранить их обозначения, значения, единицы и статусы.

**Проверка 3. Сверка**

Сравнить PV с дисплеем Метрана.

При нулевом перепаде ожидается небольшое значение около нуля, но не фиксированное постоянное число.

**Проверка 4. Непрерывный мониторинг**

Запустить мониторинг примерно на пять минут.

Проверить отсутствие искусственных данных и корректность графика.

**Проверка 5. Фоновая работа**

Свернуть приложение, погасить экран, затем вернуться.

Проверить сохранение сессии и непрерывность опроса в пределах возможностей Android.

**Проверка 6. Ручное сохранение**

Сохранить сессию.

Открыть её в журнале.

Проверить график и временные метки.

**Проверка 7. Восстановление**

Только в безопасных разрешённых условиях проверить кратковременную потерю Bluetooth.

Проверить восстановление и разрыв на графике.

**Проверка 8. Таймаут**

На лабораторном стенде проверить 60-секундный таймаут и диалог выбора.

**Проверка 9. Диагностика**

Скопировать журнал TX/RX и событий сессии.

Не проверять операции записи на этом этапе.

Если испытание с намеренным обрывом связи нельзя провести безопасно, пропустить его и явно обозначить как непроверенное. Остальные результаты от этого не становятся недействительными.
