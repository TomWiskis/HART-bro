# Архитектура этапа 1

```text
app / Compose → SessionViewModel → HartClient → HartTransport
                                    ↓              ↑
                              HartDecoder    BluetoothSppTransport
                              DeviceIdentity       ↓
                              PrimaryVariable   Android RFCOMM
```

`hart-core` — самостоятельный Kotlin/JVM-модуль без Android. Адресация, кодек, идентификация и PV отделены от транспорта. `HartClient` последовательно выполняет запросы через `Mutex`; его публичный API содержит только `identify()` и `primaryVariable()`. Конструктор кадра принимает enum с двумя безопасными командами, без произвольного номера или payload. Поддержки записи в production-коде нет.

`transport-bluetooth` — Android library, реализующая `HartTransport`. Сопряжение и выбор устройства принадлежат Android/UI, а не кодеку. Соединение — secure SPP/RFCOMM с таймаутом и закрытием сокета при отмене. Отдельный IO-reader складывает фрагменты в ограниченный канал. Серийные настройки USB/UART к Android BluetoothSocket неприменимы; никаких предположительных управляющих последовательностей модему не посылается.

`app/session` — жизненный цикл текущего соединения и временное состояние в `StateFlow`. Новый сеанс очищает идентификацию и PV, не объединяет данные приборов. Фактический HART-статус показан отдельно. Любая ошибка делает значение PV недоступным; старое показание не выдаётся за текущее. Метка времени — время получения полного ответа телефоном, не часы датчика. Обновления экрана не создают измерений.

`app/MainActivity` — Compose Material 3, три вкладки первого этапа: связь, результат, HEX. Текущая сессия переживает пересоздание Activity при повороте. При уходе в фон соединение прекращается, постоянных фоновых процессов и хранения данных нет. Нет доступа приложения к сети, аналитики или регистрации.

## Протокол

- Запрос 0 на короткий polling address 0, primary master, 20 преамбул. Multidrop не сканируется.
- Ответ 0: проверка FE-маркера, длины минимум 12 байтов и ревизии 5–7. Длинный адрес — тип устройства (14 бит) и идентификатор (24 бита), с битом primary master.
- Для HART 5 код производителя берётся из legacy-поля; для 6/7 — из расширенной части ответа при её наличии. Торговые наименования не угадываются по кодам.
- Число преамбул следующего запроса — максимум 20 и требуемого прибором количества.
- Ответ 1: ровно 5 байтов данных: код единицы и IEEE-754 float32 big endian. NaN/Infinity не считается достоверным измерением.
- Декодер принимает обычные short/long запросы, ACK и burst-кадры. Клиент принимает только ACK с ожидаемыми адресом и номером команды; эхо и burst не считаются ответом. Разделители с expansion bytes явно отвергаются.
- Максимум две попытки чтения по 2,5 секунды. Ошибки статуса ответа и Bluetooth IO не повторяются как таймауты HART. Перед попыткой удаляются уже накопленные ответы; неполный кадр на таймауте диагностируется и сбрасывается.
- У HART нет идентификатора транзакции. Поздний ответ той же команде и тому же адресу, пришедший во время следующей попытки, физически неотличим. Поэтому повторы ограничены чтением, а время PV всегда обозначено как время приёма. Не обещается обнаружение всех запоздавших ответов.

## Расширение после отдельного задания

Профили устройств добавят достоверные названия, возможности и ограничения поверх идентификации. Measurement Engine будет пользоваться сериализованным клиентом, а не открывать параллельные соединения. Session Manager этапа 2 добавит восстановление с проверкой уникального адреса и интервалы отсутствия данных.

Хранилище Room подключается отдельным компонентом по явной команде сохранения; текущий буфер не должен автоматически переноситься в журнал. Configuration Engine потребует отдельного API подтверждённых записей с проверкой идентичности, read-back и результатом «неизвестно» при потере ответа, без автоматического повтора. Технический терминал не должен обходить эти правила. Эти компоненты не имитируются заглушками в первом прототипе.

## Тесты

Golden vectors запросов/ответов, фрагментация во всех границах, шум, контрольная сумма, недостаточная длина, переполнение, разбор идентификации/единиц/чисел, таймауты, отмена, коды ошибок, сериализация и фильтрация посторонних кадров. Симулятор транспорта существует только в `hart-core/src/test`; в APK он не включается.
