# Архитектура этапа 1

```text
app / Compose → SessionViewModel → HartClient → HartTransport
                                    ↓              ↑
                              HartDecoder    BluetoothSppTransport
                              DeviceIdentity       ↓
                              PrimaryVariable   Android RFCOMM
```

`hart-core` — самостоятельный Kotlin/JVM-модуль без Android. Адресация, кодек, идентификация и PV отделены от транспорта. `HartClient` последовательно выполняет запросы через `Mutex`; его публичный API содержит только `identify()` и `primaryVariable()`. Конструктор кадра принимает enum с двумя безопасными командами, без произвольного номера или payload. Поддержки записи в production-коде нет.

`transport-bluetooth` — Android library, реализующая `HartTransport`. Сопряжение и выбор устройства принадлежат Android/UI, а не кодеку. Соединение — secure SPP/RFCOMM с таймаутом и закрытием сокета при отмене. Отдельный IO-reader складывает фрагменты в ограниченный канал. Серийные настройки USB/UART к Android BluetoothSocket неприменимы; никаких предположительных управляющих последовательностей модему не посылается.

`app/session` — жизненный цикл текущего соединения и временное состояние в `StateFlow`. Новый сеанс очищает идентификацию и PV, не объединяет данные приборов. Фактический HART-статус показан отдельно. Любая ошибка делает значение PV недоступным; старое показание не выдаётся за текущее. Метка времени — время получения полного ответа телефоном, не часы датчика. Обновления экрана не создают измерений.

`app/MainActivity` — Compose Material 3, три вкладки первого этапа: связь, результат, HEX. Текущая сессия переживает пересоздание Activity при повороте. При уходе в фон соединение прекращается, постоянных фоновых процессов и хранения данных нет. Нет доступа приложения к сети, аналитики или регистрации.

## Протокол

- Запрос 0 на короткий polling address 0, primary master, 20 преамбул. Multidrop не сканируется.
- Ответ 0: проверка FE-маркера, длины минимум 12 байтов и ревизии 5–7. Сохраняется полный 16-битный тип устройства и 24-битный ID. Только при построении длинного wire-адреса два старших бита первого байта типа заменяются битами ведущего/burst. Для дампа Метрана тип `9972`, ID `5FCA7F`, адрес primary master `99 72 5F CA 7F`.
- Для HART 5 код производителя берётся из полного 8-битного legacy-поля; для 6/7 — из двух байтов расширенной части ответа при её наличии. Имя производителя есть в небольшой явной таблице; неизвестные коды и названия моделей не угадываются. Версии HART и команд устройства отображаются отдельно.
- Число преамбул следующего запроса — максимум 20 и требуемого прибором количества.
- Ответ 1: ровно 5 байтов данных: код единицы и IEEE-754 float32 big endian. NaN/Infinity не считается достоверным измерением.
- Декодер принимает асинхронные short/long STX, ACK и burst-кадры, включая 0–3 expansion bytes между адресом и командой. Неизвестные expansion bytes сохраняются без смысловой интерпретации; PSK/другие physical-layer коды не поддержаны. Клиент принимает только ACK с ожидаемыми адресом и номером команды; эхо и burst не считаются ответом.
- Накопительный буфер сохраняет преамбулу, заголовок и частичный payload между фрагментами, включая пустые. Отдельные пакеты Bluetooth не трактуются как HART-кадры. Четыре преамбулы допускаются как совместимость с реальным дампом VIATOR/Метран, с `WARN` после полной проверки XOR и длины; менее четырёх отвергаются. Требования к исходящим преамбулам не ослаблены.
- Пока заявленная длина не набрана, payload не сканируется на «новую» преамбулу: внутри данных тоже могут быть `FF`. Сильно завышенная повреждённая длина может ждать таймаута; тогда неполный кадр логируется и явно сбрасывается перед следующей попыткой. При неверной сумме полного кадра выполняется повторный поиск синхронизации. Буфер ограничен 8192 байтами; переполнение — отдельная ошибка.
- `RX-CHUNK` показывает исходные фрагменты, `RX-FRAME` — собранный полный кадр с преамбулой и XOR, `TX-FRAME` — полный запрос. Коды ответов, все восемь флагов device status и идентификация расшифровываются в диагностике; прибору не отправляется команда сброса статуса.
- Максимум две попытки чтения по 2,5 секунды. Ошибки статуса ответа и Bluetooth IO не повторяются как таймауты HART. Перед попыткой удаляются уже накопленные ответы; неполный кадр на таймауте диагностируется и сбрасывается.
- У HART нет идентификатора транзакции. Поздний ответ той же команде и тому же адресу, пришедший во время следующей попытки, физически неотличим. Поэтому повторы ограничены чтением, а время PV всегда обозначено как время приёма. Не обещается обнаружение всех запоздавших ответов.

## Расширение после отдельного задания

Профили устройств добавят достоверные названия, возможности и ограничения поверх идентификации. Measurement Engine будет пользоваться сериализованным клиентом, а не открывать параллельные соединения. Session Manager этапа 2 добавит восстановление с проверкой уникального адреса и интервалы отсутствия данных.

Будущий USB-HART ЭнИ-406 (настольный, mini-USB, без питания датчика) сможет реализовать тот же независимый `HartTransport`. В 0.1.1 USB OTG, драйвер, разрешения USB и питание петли этим модемом не реализуются; работает только Bluetooth VIATOR.

Хранилище Room подключается отдельным компонентом по явной команде сохранения; текущий буфер не должен автоматически переноситься в журнал. Configuration Engine потребует отдельного API подтверждённых записей с проверкой идентичности, read-back и результатом «неизвестно» при потере ответа, без автоматического повтора. Технический терминал не должен обходить эти правила. Эти компоненты не имитируются заглушками в первом прототипе.

## Тесты

Golden vectors запросов/ответов, фрагментация во всех границах, шум, контрольная сумма, недостаточная длина, переполнение, разбор идентификации/единиц/чисел, таймауты, отмена, коды ошибок, сериализация и фильтрация посторонних кадров. Симулятор транспорта существует только в `hart-core/src/test`; в APK он не включается.

Реальный 33-байтовый ответ Метрана хранится в `hart-core/src/test/resources/metran-command0.hex`. Проверяются все разбиения, побайтовый приём, 250 детерминированных случайных фрагментаций, повреждения и неполные пакеты. Клиент воспроизводит этот ответ и синтетическую PV в 30 вариантах фрагментации; отдельно проверяется полный RX-журнал и длинный адрес команды 1.

## Развитие 0.2.0

Версия 0.1.1 выше описывает исходную реализацию. В 0.2.0 жизненный цикл сессии перенесён из Activity/ViewModel в `MonitoringService` (`connectedDevice`) и `SessionController` уровня Application. Activity больше не закрывает Bluetooth при `onStop`; ViewModel — фасад наблюдения. Служба запускается действием пользователя после согласия, не экспортируется и возвращает START_NOT_STICKY. Сессия завершается с закрытием транспорта, отменой единственного job, удалением временной истории и остановкой службы. Системная остановка не обещает автоматического продолжения.

В `hart-core` добавлены `Measurements.kt` (универсальные цифровые значения/качество и определение возможностей), `MonitoringEngine.kt` (один последовательный coroutine-цикл, интервалы, пауза, ошибки, 60-секундное восстановление и проверка идентификатора), `SessionHistory.kt` (временный ограниченный бинарный журнал + атомарные ручные снимки версии 1), `ChartViewport.kt` (проверяемая навигация по одной оси времени). Интерфейсы `MonitorConnection`/`SessionSink` позволяют проверять цикл без Android/оборудования. У HART по-прежнему одна mutex-очередь. BluetoothSppTransport не переписан, USB не добавлен.

Записи журнала содержат все values, units, quality, codes, classes, statuses, источник-команду и timestamps, loop current/extended status/ticks при наличии, а заголовок — unique ID, производителя, исходный ответ идентификации и коммуникатор. Временные данные находятся в `filesDir/active-session`, ручные снимки в `filesDir/sessions`. Снимок копируется в .partial, синхронизируется на диск и переименовывается; опубликованная запись больше не меняется. Снимки одной продолжающейся сессии имеют отдельные archive ID. Сам факт записи временного журнала не добавляет запись в пользовательский архив. При повторном запуске процесса временные остатки удаляются; архив не удаляется. Предел временной истории — 64 МиБ, после достижения требуется решение, данные не заменяются нулями и не сбрасываются молча.

`MonitoringChart` строит один Canvas с общей осью X и отдельными диапазонами для slot/unit. Читает окна на Dispatchers.IO, не хранит весь журнал в Compose. Первая/экстремальные/последняя точки корзин ограничивают объём представления (до 4 точек × 300 корзин × 4 серии); разрывы кодируются до прореживания. Качество, отсутствие слота и смена единицы меняют сегмент только соответствующей серии; сессионные ошибки/паузы/восстановление меняют общий сегмент. Между сегментами линии не проводятся. Сам архив не прореживается.

Сохранение/завершение сериализованы отдельно от опроса; снимок выполняется под блокировкой журнала. Служба держит видимое уведомление, wake lock с таймаутом 10 минут возобновляется через 5 минут только во время активной работы; при ожидании решения освобождается. Ограничения прошивки Android и реальная работа Bluetooth/Doze проверяются на телефоне по плану 0.2.0.

## Исправления 0.2.1

`ChartViewport` сохраняет span при zoom/follow, `.seek` и `.all` используют одну модель окна. `ChartAxes` выдаёт числовые/временные деления; совместимые unitCode разделяют шкалу Y, несовместимые имеют разные шкалы на одном Canvas. `SessionHistory.window` возвращает данные/домен/диапазон согласованно под одной блокировкой. Источник live-домена — последняя фактически полученная пачка, не время информационного события. UI читает через conflated-поток с ограничением частоты и отменой только при смене окна/экрана.

Для чтения временного/архивного файла построен инкрементальный индекс: контрольные точки каждые 128 записей содержат offset и состояние сегментов/единиц. Обновления читают только дописанный хвост, затем нужный диапазон; память ограничена данными индекса и прореженным окном, кеш — тремя файлами. При обнаружении немонотонных временных меток быстрый поиск не применяется, чтобы не пропускать данные. Архивы не переписываются. В version 1 добавлены type 4 (разрыв с текстом) и type 5 (информация); legacy type 2 различается по известным сообщениям потери/паузы, а не считается разрывом всегда.

`RecoveryProgress` содержит один start/deadline монотонного времени, причину, elapsed/remaining и последнюю попытку. Тикер только отображает разницу с тем же deadline, который ограничивает withTimeout; он не продлевает восстановление и не запускает повторное чтение графика каждую секунду. `MeasurementReader` временно исключает необязательный способ после двух последовательных чистых таймаутов в данной сессии. Ошибки/неполные кадры и явные response codes отделены; новое устройство/сессия снова определяет возможности, успешная 9 сохраняется.

`DiagnosticJournal` — один рабочий UTF-8-файл 16 МиБ в filesDir с явным флагом неполноты. RX-CHUNK включаются пользователем. Экспорт через SAF/ограниченный FileProvider cache-path выполняется по запросу; очистка подтверждается. Рабочий журнал не удаляется автоматически при завершении сессии/процесса. Служба логирует свой жизненный цикл, Activity пишет только наблюдения и не закрывает мониторинг. Уведомления фильтруются по состоянию мониторинга вместо общей StateFlow, содержащей RX-фрагменты. Пустой service intent при активной сессии не вызывает stopSelf. START_NOT_STICKY и отсутствие скрытого автоперезапуска сохранены.
