# ТЗ: Android HART Communicator

**Версия документа:** 1.0  
**Статус:** согласованная концепция, начало разработки  
**Язык приложения:** русский  
**Платформа:** Android  
**Первое оборудование:** Pepperl+Fuchs VIATOR Bluetooth HART Interface, HM-MT-BT-EX-010041

## 1. Цель проекта

Разработать автономное Android-приложение для диагностики, мониторинга и полноценной настройки промышленных HART-устройств.

Приложение должно обеспечивать максимально возможный доступ к параметрам, которые конкретное устройство поддерживает для чтения и записи.

На первоначальном этапе использовать промышленные датчики давления и температуры. В дальнейшем предусмотреть расширение на другие классы HART-оборудования без переработки основной архитектуры.

Интерфейс должен быть удобен для повседневной работы инженера, но содержать дополнительные инструменты для исследования HART-протокола.

**Основные принципы:**

- Полноценная работа без интернета.
- Отсутствие обязательных облачных сервисов и регистрации.
- Явное согласие пользователя на подключение.
- Явное подтверждение перед любыми операциями записи.
- Отсутствие автоматического сохранения истории проверок.
- Поддержка технической диагностики на уровне отдельных HART-команд.
- Модульная и расширяемая архитектура.

## 2. Технологическая архитектура

Предпочтительный стек:

- Kotlin.
- Jetpack Compose и Material 3.
- Нативный Bluetooth Classic API Android.
- RFCOMM / Serial Port Profile (SPP).
- Корутины и StateFlow для управления асинхронными операциями.
- Room для локального хранения сохранённых проверок и шаблонов.
- Отдельный модуль HART-протокола, независимый от Android-интерфейса.

Поддерживать Android 10 и новее. Target SDK выбрать актуальный стабильный, с соблюдением действующих требований Android.

Разделить программу на независимые компоненты:

1. Bluetooth Transport — связь с модемом.
2. HART Protocol — формирование, отправка и разбор пакетов.
3. Device Identification — определение устройства и поддерживаемых возможностей.
4. Device Profiles — расширяемая поддержка конкретных моделей.
5. Measurement Engine — опрос измерений.
6. Configuration Engine — чтение и запись параметров.
7. Session Manager — управление активной сессией.
8. Local Storage — журнал и шаблоны.
9. UI — интерфейс пользователя.
10. Diagnostic Terminal — техническая диагностика и ручные команды.

Не связывать код HART-протокола напрямую с конкретной моделью Bluetooth-модема.

## 3. Подключение

Использовать Bluetooth Classic SPP, не BLE.

При запуске приложение ищет доступный ранее сопряжённый VIATOR, но **не подключается автоматически**.

После обнаружения показать окно:

**«Обнаружен коммуникатор VIATOR. Продолжить подключение?»**

Кнопки:

- Продолжить подключение.
- Отмена.

Если доступно несколько коммуникаторов, позволить выбрать нужный.

При первом использовании поддерживать стандартную процедуру сопряжения Android.

После подтверждения:

1. Установить RFCOMM-соединение.
2. Инициализировать HART-обмен.
3. Отправить команду идентификации.
4. Получить уникальный идентификатор устройства.
5. Определить поддерживаемую версию HART.
6. Прочитать доступные параметры.
7. Перейти на экран мониторинга.

Каждый датчик подключён к отдельному измерительному каналу. В первоначальной версии полноценный многоточечный поиск HART-устройств не нужен.

При этом внутренняя адресация HART должна реализовываться корректно, включая получение уникального адреса и последующее обращение к идентифицированному устройству.

При неудачном подключении показать понятную причину: Bluetooth недоступен, устройство выключено, соединение отклонено, HART-ответ отсутствует и т. д.

## 4. Работа с HART

Реализовать формирование и разбор кадров HART с учётом версий протокола.

Обязательные функции:

- Работа с короткой и длинной адресацией.
- Преамбулы и структура кадров.
- Контроль длины сообщений.
- Проверка контрольных сумм.
- Обработка кодов ответа и статусов.
- Обработка неполных, ошибочных и запоздавших кадров.
- Очередь запросов без конкурирующих команд в одной сессии.
- Таймауты и ограниченные повторные попытки для безопасных операций чтения.
- Запрет автоматического повторения команд записи при неопределённом результате.

Сначала реализовать универсальные команды, затем общепринятые.

Предусмотреть поддержку специфичных команд производителей посредством профилей.

Не считать, что любой прибор поддерживает все команды. Доступные функции определять по версии HART, ответам устройства и описанию конкретной модели.

Поддержку DD/EDD спроектировать как перспективное расширение; на первом этапе не разрабатывать полноценный интерпретатор.

## 5. Мониторинг измерений

Главный экран должен отображать:

- Тип подключённого прибора.
- Производителя и модель.
- TAG.
- Статус связи.
- Основной измеряемый параметр.
- Дополнительные измеряемые параметры.
- Единицы измерения.
- Состояние прибора.
- Информацию о сообщаемом датчиком токовом выходе.
- Единый график измерений.

**Важно:** значения измеряемых величин получать непосредственно из цифровых ответов HART. Не рассчитывать давление, температуру или другие величины из тока 4–20 мА.

Для дополнительных переменных использовать поддерживаемые устройством HART-команды.

Все выбранные пользователем измеряемые параметры отображать на одном графике.

Предусмотреть:

- Выбор отображаемых линий.
- Легенду.
- Корректные единицы измерения.
- Независимое масштабирование разных физических величин.
- Временную шкалу.
- Масштабирование и перемещение по времени.
- Просмотр значений конкретных точек.
- Фактические временные метки измерений.

Отдельные графики для каждой величины не создавать.

Токовый выход отображать как самостоятельный диагностический показатель, не использовать его для расчёта цифровых измерений.

Частоту обновления определять по реальной скорости HART-обмена. Не создавать искусственные промежуточные измерения.

## 6. Потеря связи и восстановление

При обнаружении потери Bluetooth или устойчивого отсутствия HART-ответов:

1. Приостановить получение измерений.
2. Зафиксировать начало интервала отсутствия связи.
3. Прервать линии графика на соответствующем временном интервале.
4. Запустить асинхронное восстановление связи.
5. Ограничить период автоматического восстановления 60 секундами.

Если Bluetooth остаётся подключённым, но HART-датчик перестал отвечать, сначала предпринимать повторную HART-инициализацию без ненужного разрыва Bluetooth.

При восстановлении:

- Проверить идентичность HART-устройства.
- Продолжить прежнюю сессию.
- Возобновить отображение новых измерений.
- Сохранить разрыв на графике без интерполяции.

Если обнаружен другой датчик — не объединять его измерения с прежней сессией.

При истечении 60 секунд вывести диалог:

**«Связь не восстановлена»**

Варианты:

- Сохранить сессию.
- Завершить без сохранения.

Ни одно действие не выполнять автоматически.

Если приложение свёрнуто, использовать поддерживаемый Android механизм продолжительной Bluetooth-работы и восстановления соединения с соответствующим системным уведомлением.

Повторно запрашивать разрешение подключения в течение восстановления той же сессии не требуется.

## 7. Журнал проверок

Журнал является отдельным разделом.

**Автоматически сохранять подключения, измерения и проверки в постоянный журнал запрещено.**

Во время подключения приложение накапливает данные текущей сессии во временном рабочем буфере.

Сохранение осуществляется только после нажатия пользователем кнопки «Сохранить проверку» или согласия сохранить завершаемую сессию.

Сохраняемая проверка включает:

- Дату и время.
- Продолжительность.
- Идентификатор прибора.
- Производителя и модель.
- TAG.
- Снимок доступной конфигурации.
- Измерения с временными метками.
- Единицы измерения.
- График за время подключения до момента сохранения.
- Интервалы отсутствия данных.
- Статусы и ошибки.
- Необязательный комментарий пользователя.

Предусмотреть просмотр, переименование и удаление проверки.

Предусмотреть удаление нескольких проверок и очистку всего журнала с подтверждением.

В журнале отображать единый график сохранённых измеряемых параметров.

Дополнительно реализовать сравнение:

- Двух сохранённых проверок одного устройства.
- Текущей конфигурации с ранее сохранённой.

Показывать изменившиеся конфигурационные параметры со значениями «Было» и «Стало».

Текущие измерения не трактовать как изменение конфигурации.

## 8. Экспорт

Реализовать:

**PDF**

Формирование читаемого отчёта с идентификацией прибора, датами, параметрами, графиком, ошибками и результатами проверки.

**CSV**

Экспорт фактических измерений и временных меток в формат, пригодный для открытия в Microsoft Excel.

Поддерживать UTF-8 и кириллицу, корректные заголовки и единицы измерения.

Экспорт выполнять только по явному действию пользователя.

В перспективе предусмотреть XLSX без обязательной реализации в первой версии.

## 9. Чтение и запись конфигурации

Приложение должно предоставлять максимально доступное чтение и запись поддерживаемых параметров.

Возможные категории:

- Диапазоны измерений.
- Единицы.
- Демпфирование.
- TAG и описательные поля.
- Коммуникационные настройки.
- Поддерживаемые сервисные функции.
- Диагностика.
- Калибровочные операции.
- Специфичные параметры производителя.

Учитывать допустимые значения и ограничения конкретного устройства.

Каждая запись выполняется по последовательности:

1. Пользователь изменяет значение.
2. Нажимает «Установить».
3. Появляется окно подтверждения с прежним и новым значениями.
4. Пользователь нажимает «Да».
5. Приложение отправляет команду записи.
6. Повторно считывает соответствующий параметр.
7. Показывает подтверждённый результат.

При отсутствии ответа на запись не повторять её автоматически, поскольку неизвестно, выполнена ли она прибором. Сначала проверить фактическое состояние.

Для потенциально опасных операций показывать дополнительное предупреждение о возможном влиянии на технологический процесс.

## 10. Шаблоны конфигураций

Разработать отдельное хранилище шаблонов, не связанное с журналом проверок.

Позволить:

- Считать конфигурацию датчика.
- Сохранить её как шаблон по явному действию.
- Присвоить имя и описание.
- Выбрать шаблон для другого датчика.
- Сравнить исходную и целевую конфигурации.
- Выбрать параметры для переноса.
- Подтвердить применение.
- Проверить результаты записи.

Не переносить:

- Уникальные идентификаторы.
- Заводские серийные номера.
- Индивидуальные заводские коэффициенты калибровки.
- Текущие измерения.
- Параметры, не поддерживаемые целевым устройством.

Для различных моделей проверять совместимость единиц, диапазонов, возможностей и ограничений.

Перед записью отображать итоговый перечень изменений.

При частичном выполнении операции показывать, какие параметры успешно применены, а какие нет.

Не пытаться автоматически откатывать изменения без проверки фактического состояния.

## 11. Технические карточки параметров

Для каждого поддерживаемого параметра предусмотреть кнопку информации.

Карточка включает:

- Инженерное название и назначение.
- Текущее значение и единицы.
- Возможность чтения и записи.
- Номер и описание HART-команды чтения.
- Номер и описание HART-команды записи, если доступна.
- Формат кодирования.
- Сырые данные в HEX.
- Расшифровку полей ответа.
- Статус последнего обмена.
- Переход в HART Terminal.

Не показывать весь технический материал на основных экранах. Карточки открываются только по запросу.

Неизвестные структуры данных не расшифровывать догадками.

## 12. HART Terminal

Реализовать экспертный инструмент для работы с протоколом.

Функции:

- Выбор команды HART.
- Указание аргументов.
- Формирование пакета.
- Просмотр отправленных и полученных байтов.
- Расшифровка структуры сообщения.
- Отображение времени ответа.
- Отображение кодов ошибок.
- Копирование HEX.
- Ручное повторение команд.
- Экспорт технического лога только по запросу.

Команды записи требуют явного подтверждения, в том числе при отправке через терминал.

Неизвестные команды не должны автоматически классифицироваться как безопасные.

Терминал необходим для исследования протокола, добавления новых профилей и разработки собственных HART-устройств.

Важные операции требуют подтверждения, но обычное чтение параметров не должно быть перегружено диалоговыми окнами.

Поддерживать светлую и тёмную темы.

Интерфейс должен корректно работать на обычных Android-смартфонах.

## 14. Безопасность

Первоначальные испытания проводить на отдельной лабораторной токовой петле, а не на действующей автоматике.

Приложение не должно:

- Самостоятельно изменять параметры.
- Выполнять незапрошенные команды записи.
- Автоматически запускать калибровку.
- Самостоятельно менять адреса.
- Повторять неподтверждённые операции записи.
- Скрывать отсутствие достоверных данных.
- Объединять результаты различных приборов.

Предусмотреть надёжную идентификацию целевого устройства перед записью.

При невозможности подтвердить идентичность прибора — запретить изменение параметров.

Соблюдать требования безопасности HART-оборудования, токовых петель и взрывоопасных зон.

## 15. Этапы реализации

### Этап 1. Прототип связи

Реализовать:

- Базовый интерфейс Android.
- Поиск ранее сопряжённого VIATOR.
- Подтверждение подключения.
- Bluetooth Classic RFCOMM/SPP.
- Приём и передачу данных.
- Базовый HART-кодек.
- Команду идентификации №0.
- Обработку ответов и ошибок.
- Определение производителя, модели и версии протокола по доступным данным.
- Чтение основной измеряемой переменной.
- Простой экран результатов.
- Диагностический просмотр HEX для исследования связи.

На этом этапе **не реализовывать команды записи в реальные приборы**.

Создать тесты кодирования и декодирования HART-пакетов, включая ошибочные и неполные кадры.

При несовместимости или неполной документации модема не имитировать успешную работу, а сохранять диагностическую информацию и явно указывать, что требует проверки на аппаратуре.

**Критерий готовности:** приложение устанавливает реальное соединение с VIATOR, получает корректный ответ HART от подключённого датчика и показывает его цифровую измеряемую величину.

### Этап 2. Мониторинг и сессии

- Все доступные измеряемые переменные.
- Единый график.
- Управление отображаемыми линиями.
- Обработка потери связи.
- Восстановление за 60 секунд.
- Разрывы графика.
- Управление сессией.

### Этап 3. Журнал и экспорт

- Ручное сохранение проверок.
- Локальный журнал.
- Просмотр графиков.
- Удаление.
- Сравнение конфигураций.
- PDF и CSV.

### Этап 4. Конфигурирование

- Поддерживаемые команды чтения/записи.
- Подтверждения изменений.
- Проверка записанного значения.
- Диагностика.
- Сервисные операции.
- Шаблоны конфигураций и перенос параметров.

### Этап 5. Экспертные возможности

- Технические карточки.
- Полноценный HART Terminal.
- Расширяемые профили устройств.
- Специфичные команды производителей.
- Подготовка архитектуры для будущих собственных HART-устройств.

## 16. Требования к работе Codex

**Сейчас реализовать исключительно этап 1.**

При этом основную архитектуру строить с учётом всех требований настоящего ТЗ.

Не подменять реальный Bluetooth и HART фиктивными данными.

Допускаются отдельные тестовые симуляторы, но режим симуляции должен быть явно обозначен и не смешиваться с подключением к настоящему оборудованию.

Не добавлять неподтверждённые команды записи.

При необходимости изучить документацию устройства и официальные требования Android.

Создать:
