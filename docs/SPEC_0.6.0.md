# Техническое задание для Codex
## HART-бро 0.6.0 — интеграция ЭнИ-406 через USB OTG и оптимизация обхода датчиков

### 1. Цель этапа

Расширить существующее Android-приложение HART-бро поддержкой второго HART-коммуникатора — ЭнИ-406 через USB OTG — и ускорить существующий режим обхода датчиков.

Разработку вести на базе актуальной версии приложения. Не переписывать работающие компоненты без необходимости.

**Основные результаты:**
1. Приложение работает с двумя коммуникаторами: Pepperl+Fuchs/MACTek VIATOR через Bluetooth Classic SPP и ЭнИ-406 через USB OTG.
2. Один HART-движок обслуживает оба транспорта.
3. Все существующие режимы доступны через оба коммуникатора.
4. Обход датчиков работает быстрее, не изменяя назначения и формата собираемых данных.
5. Существующие функции VIATOR не нарушены.

Не выполнять косметическую переработку интерфейса.

---

### 2. Поддерживаемое оборудование

**Устройство № 1 — VIATOR Bluetooth HART Modem**
- Существующее подключение Bluetooth Classic, профиль SPP/RFCOMM.
- Полностью сохранить текущую функциональность.
- Не заменять Bluetooth Classic на BLE.
- Не изменять без необходимости работающие механизмы обмена.

**Устройство № 2 — ЭнИ-406**
- Настольный HART-модем с разъёмом mini-USB.
- Исполнение пользователя — без встроенного источника питания токовой петли.
- Соединение со смартфоном через USB OTG.
- Питание самого модема от USB смартфона.
- Питание датчика — от существующей внешней токовой петли или лабораторного источника питания.
- Не предполагать наличие встроенного питания 24 В.
- Не разрабатывать управление аппаратным питанием петли через Android.

При разработке учитывать возможность существования нескольких аппаратных ревизий ЭнИ-406.

### 2.1. Определение USB-интерфейса

До выбора драйвера необходимо определить фактический тип USB-устройства.

Руководство производителя упоминает FTDI, однако для разных аппаратных ревизий доступны разные драйверы.

Поэтому:
- Получать реальные USB VID/PID.
- Читать доступные USB-дескрипторы.
- Определять количество интерфейсов и их тип.
- Выбирать соответствующий драйвер USB Serial.
- Предусмотреть поддержку FTDI и, при необходимости, других реально обнаруженных контроллеров.
- Не назначать заранее выдуманные VID/PID.
- Не считать устройство совместимым с произвольным драйвером без проверки.

Использовать Android USB Host API и подходящую библиотеку USB Serial, если она совместима с фактическим оборудованием.

Не требовать root-доступа, системной установки драйверов Windows или дополнительных привилегий Android.

### 2.2. Параметры последовательного соединения

Настройки USB Serial должны включать:
- Скорость передачи.
- Количество бит данных.
- Чётность.
- Стоповые биты.
- Управление потоком, если необходимо.

Не путать скорость физического HART-канала 1200 бит/с со скоростью виртуального последовательного USB-порта.

Параметры USB-порта устанавливать по подтверждённой документации или результатам испытаний.

В диагностическом режиме предусмотреть отображение фактически выбранных параметров.

Не использовать автоматический перебор настроек, способный создавать неконтролируемую последовательность HART-запросов.

### 3. Архитектура транспорта

Выделить общий интерфейс транспортного уровня.

Он должен обеспечивать:
- Открытие соединения.
- Закрытие соединения.
- Передачу массивов байтов.
- Приём произвольных фрагментов данных.
- Контроль ошибок.
- Уведомление о физическом отключении.
- Состояние подключения.
- Корректное освобождение ресурсов.

Реализовать два независимых адаптера:

**BluetoothHartTransport**
- Использует существующее соединение VIATOR по Bluetooth Classic.
- Максимально переиспользует проверенный код.

**UsbHartTransport**
- Использует Android USB Host API.
- Работает с выбранным USB Serial драйвером.
- Поддерживает обработку подключения и отключения USB.

Общий HART-движок не должен знать, какой транспорт используется.

Схема взаимодействия:

Android UI  
↓  
Session / Walk / Quick View  
↓  
HART Engine  
↓  
Transport Interface  
├── Bluetooth SPP — VIATOR  
└── USB Serial — ЭнИ-406

Сохранить существующий парсер HART, проверку XOR, обработку фрагментированных ответов и уже подтверждённую совместимость с приборами, возвращающими четыре байта преамбулы FF.

Не создавать отдельные реализации HART-команд для USB и Bluetooth.

### 4. Подключение ЭнИ-406

#### 4.1. Обнаружение

При подключении USB-модема:
1. Android обнаруживает USB-устройство.
2. Приложение получает идентификаторы и дескрипторы.
3. Определяет доступный USB Serial интерфейс.
4. Показывает обнаруженное устройство.
5. Запрашивает разрешение Android.
6. После разрешения открывает соединение.
7. Переводит транспорт в состояние готовности.

Не запускать автоматически измерительную сессию.

При отсутствии физического USB-устройства не пытаться открыть несуществующий последовательный порт.

#### 4.2. Разрешения Android

Использовать штатный механизм USB permission request.

Обработать:
- Разрешение предоставлено.
- Разрешение отклонено.
- Запрос закрыт пользователем.
- Устройство отсоединено до завершения запроса.
- Устройство физически отключено при работающем приложении.
- USB-интерфейс занят или недоступен.

Не допускать циклического открытия системного диалога разрешений.

После повторного подключения разрешение запрашивать только тогда, когда это требуется системой.

#### 4.3. Выбор коммуникатора

На странице подключения обеспечить выбор:
- VIATOR — Bluetooth.
- ЭнИ-406 — USB.

Показывать только фактически доступные экземпляры устройств или понятное состояние их отсутствия.

Не переключать активный транспорт автоматически при подключении второго модема, если уже идёт рабочая сессия.

Переключение выполнять по действию пользователя.

Не допускать параллельного управления одной HART-сессией двумя модемами.

#### 4.4. Работа соединения

После успешного USB-подключения должны быть доступны:
- Быстрый просмотр конфигурации.
- Обычная идентификация датчика.
- Полноценная измерительная сессия.
- Диагностика.
- Чтение и поддерживаемая запись параметров.
- Калибровка нуля с существующими проверками безопасности.
- Обход датчиков.
- Журнал и экспорт данных.

Не создавать отдельный USB-интерфейс приложения с урезанной функциональностью.

### 5. Разделение состояния транспорта и HART

Приложение должно отдельно отслеживать:

**Состояние коммуникатора**
- Bluetooth подключён или отключён.
- USB подключён или отключён.
- Ошибка открытия USB Serial.
- Физическое отсоединение USB.
- Потеря Bluetooth.

**Состояние HART-датчика**
- Датчик обнаружен.
- Датчик отвечает.
- Датчик не отвечает.
- Прибор заменён.
- Выполняется опрос.
- Произошла ошибка HART.

Подключённый ЭнИ-406 без обнаруженного датчика — нормальное состояние.

Не показывать потерю USB-соединения, когда USB-модем работает, но датчик не отвечает.

Индикация должна использовать существующий визуальный стиль приложения.

#### 5.1. Отключение USB во время измерений

При физическом отключении:
- Немедленно остановить передачу новых запросов.
- Закрыть транспорт.
- Зафиксировать событие.
- Сохранить уже накопленные данные в памяти текущей сессии.
- Отобразить разрыв на графике.
- Не подставлять нулевые или выдуманные измерения.
- Не удалять историю автоматически.

Если тот же модем подключён повторно, допускать восстановление в рамках существующего 60-секундного окна переподключения после получения разрешения USB и проверки идентичности HART-датчика.

Не возобновлять запись параметров автоматически, если ответ на ранее отправленную команду записи был потерян.

### 6. Диагностика USB

Расширить существующий HEX-журнал.

Для USB фиксировать:
- Время обнаружения.
- VID/PID.
- USB-интерфейс и выбранный драйвер.
- Параметры последовательного порта.
- Время открытия соединения.
- TX/RX HART-кадры.
- Ошибки чтения и записи.
- Таймауты.
- Физическое отключение.
- Повторное подключение.
- Причину закрытия транспорта.

Различать ошибки:
- USB device not found.
- USB permission denied.
- USB Serial open failed.
- USB read/write failed.
- HART timeout.
- HART response error.
- Invalid HART frame.

Подробные побайтовые фрагменты RX сохранять только при включённой расширенной отладке.

В обычном журнале достаточно полных HART-кадров и диагностических событий.

# Часть II. Оптимизация обхода датчиков

### 7. Принцип оптимизации

**Не изменять назначение режима обхода.**

Он предназначен для последовательного сбора данных полевых приборов и формирования экспортируемой таблицы.

Не объединять обход с быстрым просмотром конфигурации.

Не превращать обход в полноценную измерительную сессию.

Не изменять пользовательскую последовательность подтверждения и добавления устройств без необходимости.

Цель оптимизации — уменьшить ожидание при обнаружении и количество лишних HART-запросов.

---

### 8. Оптимизация обнаружения датчика

Согласно предыдущему диагностическому журналу, при отсутствии ответа одна попытка обнаружения занимала примерно:
- 1500 мс — таймаут HART.
- 1200 мс — дополнительная пауза.

Итого около 2700 мс.

Изменить алгоритм:

- Сохранить начальный HART-таймаут обнаружения 1500 мс.
- Уменьшить дополнительную паузу после неудачной попытки до 300–500 мс.
- Не отправлять следующий запрос до завершения предыдущего.
- Не накапливать очередь просроченных команд.
- Отсчитывать паузу от завершения запроса.
- При успешном ответе сразу переходить к идентификации и чтению параметров.
- Не вставлять дополнительную паузу перед первой командой чтения конфигурации.

Предусмотреть возможность настройки таймаута в технической конфигурации без изменения пользовательского интерфейса.

Не уменьшать таймаут до значений, которые делают нормальные HART-ответы недостижимыми.

---

### 9. Оптимизация набора HART-команд

Сейчас обход использует в том числе:
- Команду 0 — идентификация.
- Команду 13 — TAG, descriptor и дата.
- Команду 15 — параметры выходного диапазона.
- Команду 14 — дополнительные данные сенсора.
- Команду 16 — Final Assembly Number.

Перейти к минимальному обязательному набору запросов для формирования существующей ведомости.

**Основная последовательность:**
1. Command 0 — идентификация.
2. Command 13 — TAG и дата.
3. Command 15 — параметры диапазона.

Дополнительные команды выполнять только в том случае, если их результаты реально используются в действующей ведомости или необходимы для корректного получения обязательных полей.

Не запрашивать Command 14 и Command 16 по умолчанию только ради заполнения неиспользуемых данных.

Не создавать дополнительные столбцы Final Assembly Number.

Если данные Final Assembly Number всё же нужны существующей функции, считывать их по необходимости, не показывая пустых значений.

Не исключать из ведомости уже существующие полезные параметры без проверки их источников.

### 9.1. Обработка отсутствующих ответов

Если обязательная команда не получила ответа:
- Не прерывать весь обход автоматически.
- Отметить конкретный параметр как непрочитанный.
- Сохранить успешно полученные данные.
- Предусмотреть однократное повторное чтение нужного параметра, когда это оправданно.
- Не выполнять длинные цепочки повторов без ограничений.

Если отсутствует ответ Command 15, нельзя автоматически считать, что у прибора нет диапазона.

---

### 10. Идентификация при одинаковых Device ID

В реальных испытаниях обнаружено, что несколько физически разных датчиков могут возвращать одинаковые идентификационные данные, включая Device ID.

Например, группа приборов возвращала:
- Manufacturer ID: 0x00FA.
- Device Type: 0xFAEC.
- Device ID: 000001.

Не считать такие данные автоматически ошибочными.

Не изменять прочитанные идентификаторы.

Не удалять повторяющиеся записи автоматически.

Не использовать Device ID как единственный безусловно уникальный ключ физического прибора в таблице обхода.

Для каждой строки ведомости использовать отдельный внутренний идентификатор записи.

Повторно встречающийся Device ID должен обрабатываться существующим механизмом подтверждения прибора.

Не создавать новый прибор только потому, что произошёл один кратковременный пропуск HART-ответа.

При повторном обнаружении учитывать полный идентификационный набор и последовательность событий отключения/подключения.

Если идентификация остаётся неоднозначной, решение о создании новой строки оставлять пользователю.

---

### 11. Исправление экспорта Device ID

В предыдущей ведомости серийные номера не были корректно представлены, хотя HART-идентификаторы успешно получались.

Исправить экспорт.

Device ID отображать как серийный номер в десятичной форме.

Примеры:
- HEX 000001 → 1.
- HEX BF2C34 → 12528692.

Для преобразования использовать беззнаковое числовое представление соответствующего идентификатора, полученного из HART.

Не выдавать HEX-код за десятичный серийный номер.

Не придумывать другие серийные номера и не подменять Device ID параметрами Sensor Serial Number или Final Assembly Number.

Сохранить исходный идентификатор во внутренней модели данных для протокольной работы.

**Важное условие:** не превращать поле серийного номера в уникальный ключ строки Excel.

---

### 12. Достоверность экспортируемых данных

Данные в существующей ведомости считать фактическими ответами датчиков.

Не пытаться автоматически исправлять:
- Необычные производственные коды.
- Одинаковые серийные номера.
- Необычные TAG.
- Пустые поля.
- Неизвестные Device Type.
- Нестандартно закодированные значения.

Неизвестные производители и устройства должны сохранять свои исходные коды.

Если TAG содержит байты, которые невозможно корректно декодировать, не заменять их придуманным названием.

Не подставлять дату производства из системной даты Android.

Не считать стандартное поле HART Date подтверждённой датой изготовления без соответствующих сведений от прибора.

Не изменять структуру экспортируемой таблицы, кроме точечных исправлений, необходимых для записи ранее отсутствовавшего серийного номера.

---

### 13. Уменьшение нагрузки от журналирования

Сейчас диагностический журнал содержит множество записей отдельных RX-фрагментов, иногда по одному байту.

Для обычной эксплуатации:
- Сохранять завершённые TX/RX-кадры.
- Сохранять ошибки и таймауты.
- Сохранять ключевые переходы состояний.
- Сохранять длительность операций.
- Не создавать отдельную запись для каждого полученного байта.

Для расширенной отладки:
- Разрешить подробные RX-фрагменты.
- Сохранять существующую возможность анализа фрагментации.
- Не отключать проверки целостности HART.

Измерить влияние изменений на производительность. Не считать оптимизацию доказанной без замеров.

---

### 14. Метрики производительности обхода

Добавить технические счётчики:

- Время начала и окончания обхода.
- Время обнаружения каждого прибора.
- Длительность каждой HART-команды.
- Количество успешных запросов.
- Количество таймаутов.
- Количество повторных запросов.
- Время полного чтения одного прибора.
- Количество добавленных строк.
- Количество обнаружений повторного Device ID.
- Длительность создания XLSX.

Для сравнения использовать исходный журнал, в котором 12 записей обрабатывались приблизительно за 4 минуты 43 секунды, включая ожидание физических подключений.

Не сравнивать только общую длительность обхода: она зависит от действий пользователя.

Отдельно сравнить:
1. Время обнаружения после появления ответа датчика.
2. Чистое время чтения конфигурации.
3. Длительность одной безответной попытки.
4. Накладные расходы приложения.

Цель — уменьшить время чтения одного типового датчика и ускорить обнаружение, сохраняя надёжность.

# Часть III. Совместимость и испытания

### 15. Сохранение функциональности

Все имеющиеся функции VIATOR должны продолжить работать.

Не изменять без необходимости:
- Текущий интерфейс быстрого просмотра.
- Согласованную карточку датчика.
- Логику установки нуля.
- Редактирование диапазона.
- Диагностическое окно.
- Мониторинг PV и тока.
- График с ручным перемещением и автоследованием.
- Журнал изменений.
- Сохранение измерительных сессий.
- Экспорт PDF, CSV и XLSX.
- Проверку записанных параметров повторным чтением.

Если какие-то функции ещё не завершены в предыдущем этапе, не объявлять их готовыми автоматически.

### 15.1. Совместимость данных

### 16. Испытания USB без физического датчика

- Запрос разрешения.
- Отказ разрешения.

- Закрытие соединения.
- Отключение во время чтения.

- Отсутствие дублирования запросов.
- Отсутствие зависания потоков при отключении.

Тестовый обмен не считать подтверждением совместимости с физическим ЭнИ-406.

### 17. Реальные испытания ЭнИ-406

Провести испытания в следующем порядке.

**Этап 1 — USB**

1. Подключить ЭнИ-406 к смартфону через OTG.
2. Проверить наличие питания модема.
3. Подтвердить обнаружение USB.
4. Зафиксировать VID/PID и тип интерфейса.
5. Проверить выбор драйвера и открытие порта.

**Этап 2 — HART**

1. Подключить HART-датчик с корректно организованной токовой петлёй.
2. Выполнить Command 0.
3. Проверить идентификацию.
4. Выполнить чтение TAG и диапазона.
5. Проверить быстрый просмотр.
6. Запустить измерительную сессию.
7. Проверить PV, ток и график.

**Этап 3 — дополнительные функции**

1. Открыть диагностику.
2. Выполнить последовательное чтение параметров.
3. Проверить обход и XLSX.
4. Проверить отключение и повторное подключение USB.
5. Сравнить результаты чтения одного датчика через VIATOR и ЭнИ-406.

**Этап 4 — запись**

Проверять запись диапазона, TAG и прочие изменения только на разрешённом для настройки, безопасно подготовленном датчике.

Не выполнять калибровку нуля или изменение диапазона на работающем технологическом оборудовании без необходимых условий.

Команды записи не отправлять при первом тестировании USB, пока не подтверждена устойчивость чтения.

### 18. Тестирование оптимизации обхода

Проверить минимум следующие ситуации:

1. Датчик отсутствует — периодический поиск.
2. Датчик подключён — обнаружение и чтение.
3. Датчик отвечает медленно.
4. Команда 13 не получила ответ.
5. Команда 15 не получила ответ.
6. Датчик отключён во время чтения.
7. Датчик снова подключён.
8. Подключены два разных физических датчика с одинаковым Device ID.
9. Пользователь подтверждает повторный Device ID как новое устройство.
10. Сохранение XLSX после серии датчиков.
11. Экспорт десятичного Device ID.
12. Работа обхода через VIATOR.
13. Работа обхода через ЭнИ-406.

Проверить отсутствие утраты строк при кратковременной потере связи.

### 19. Приёмочные критерии

Задача считается выполненной при соблюдении следующих условий:

- ЭнИ-406 распознаётся Android и приложение может открыть его USB-интерфейс.
- Реальный USB Serial драйвер выбран корректно.
- Через ЭнИ-406 успешно выполняются HART-запросы и чтение конфигурации физического датчика.
- Общий HART-движок используется с обоими транспортами.
- VIATOR продолжает работать как прежде.
- Быстрый просмотр, измерительная сессия и обход доступны через оба подключения.
- Физическое отключение USB обрабатывается без аварийного завершения приложения.
- Обход выполняет меньше необязательных запросов.
- Время ожидания отсутствующего датчика снижено без недопустимого количества ложных таймаутов.
- Одинаковые Device ID не приводят к автоматической потере записей.
- XLSX содержит корректный десятичный серийный номер, если он прочитан.
- Данные датчиков не изменяются и не нормализуются самовольно.
- Приложение сохраняет существующее оформление и пользовательские данные.

Если аппаратную совместимость невозможно подтвердить без физического ЭнИ-406, чётко обозначить это в отчёте, не выдавая программные тесты за реальные испытания.
