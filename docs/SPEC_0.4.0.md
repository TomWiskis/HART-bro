# Техническое задание для Codex
## HART-бро 0.4.0 — бесшовный обход датчиков и Excel-ведомость

**Репозиторий:** https://github.com/TomWiskis/HART-bro  
**Исходная версия:** 0.3.0  
**Целевая версия:** 0.4.0  
**Платформа:** Android 10+, испытания на Android 16  
**Модем:** Pepperl+Fuchs VIATOR Bluetooth HART  
**Транспорт:** Bluetooth Classic SPP  
**Протокол:** HART 5–7  
**Режим:** исключительно чтение

# 1. Основная задача

Реализовать отдельный режим **«Обход датчиков»** для последовательной проверки большого количества промышленных HART-приборов.

Пользователь должен иметь возможность один раз подключить Bluetooth-коммуникатор VIATOR к смартфону, а затем последовательно переставлять HART-щупы между датчиками на клеммнике.

Приложение самостоятельно:

1. Обнаруживает подключённый HART-датчик.
2. Определяет его идентификатор.
3. Считывает доступные паспортные данные.
4. Получает настроенный диапазон измерений.
5. Добавляет прибор во временную таблицу обхода.
6. Обнаруживает отключение щупов.
7. Переходит в ожидание следующего прибора.
8. При подключении другого датчика повторяет процедуру.

Не требовать нажатия «Опросить», «Начать сессию», «Завершить сессию» между приборами.

По результатам обхода пользователь получает готовую ведомость Microsoft Excel в формате `.xlsx`.

**Главная цель — максимально быстрое получение сведений о большом количестве приборов с минимальным количеством действий пользователя.**

# 2. Сохранение существующего функционала

Продолжить существующий проект из GitHub. Не создавать новое приложение.

Не нарушать функции версии 0.3.0:

- Bluetooth VIATOR.
- Ручное подтверждение первоначального Bluetooth-подключения.
- HART-идентификацию.
- Потоковый приём кадров.
- Команды 0, 1, 3, 8, 9, 13, 15, 20, 48, 50.
- Непрерывный мониторинг.
- Единый график.
- Ручное сохранение измерительных сессий.
- Журнал.
- PDF и CSV.
- Просмотр сохранённых проверок.
- Сравнение конфигураций.
- Фоновую работу.
- Восстановление Bluetooth.

Новый режим должен существовать **отдельно от обычного мониторинга**.

При обычном мониторинге сохраняется ранее согласованная логика работы с одним прибором и 60-секундным восстановлением связи.

# 3. Новые HART-команды

Расширить существующий HART-движок для чтения паспортных сведений.

| Команда | Назначение |
|---|---|
| 0 | Идентификация прибора |
| 13 | Короткий TAG, описание, поле Date |
| 14 | Информация о первичном измерительном сенсоре, включая его номер |
| 15 | Настроенный диапазон измерения |
| 16 | Номер окончательной сборки (Final Assembly Number) |
| 20 | Long TAG, если поддерживается |

Повторно использовать существующие реализации команд 0, 13, 15 и 20.

Добавить недостающие команды 14 и 16 с корректной обработкой структур данных, длины ответа, контрольной суммы и кодов состояния.

Не считать номер сенсора, номер окончательной сборки и HART Device ID взаимозаменяемыми.

Для HART 5 не требовать поддержку команды 20.

Неподдерживаемая необязательная команда не должна прерывать обход.

## 3.1. Порядок идентификации

При обнаружении HART-ответа:

1. Выполнить команду 0.
2. Проверить контрольную сумму, код ответа и идентификатор.
3. Определить производителя, тип устройства, HART revision и Device ID.
4. Перейти на длинную адресацию для последующих запросов.
5. Запросить TAG.
6. Запросить настроенный диапазон.
7. Запросить доступные идентификационные номера.
8. Проверить наличие достоверных сведений о дате изготовления.
9. Сформировать результат обхода.

Не выполнять команды, не необходимые для ведомости, если это увеличивает длительность проверки.

Все запросы выполнять последовательно через существующую очередь HART.

# 4. Перечень необходимых параметров

## 4.1. TAG

Читать командой 13 или 20.

При наличии Long TAG предпочтительно использовать его.

Если оба поля пусты, отображать «Не указан» в приложении, а в Excel оставлять пустую ячейку.

Не подменять TAG идентификатором устройства.

## 4.2. Тип / марка датчика

Определять по производителю и типу устройства, возвращённым командой 0.

Использовать расширяемый справочник производителей и типов.

При неизвестной модели показывать известного производителя и код типа.

Например:

`Rosemount · тип 0x2662`

При наличии подтверждённого профиля показывать человекочитаемое название.

Не угадывать конкретную модель исключительно по производителю.

Предусмотреть ручное уточнение марки.

## 4.3. Настроенный диапазон

Использовать команду 15.

Отображение строго в компактном формате:

`0…40 кПа`

`−50…150 °C`

`0…2,5 МПа`

В основной ведомости не создавать отдельных колонок LRV и URV.

Сохранять внутренние числовые границы и исходный HART-код единицы, чтобы в дальнейшем можно было выполнять сравнения.

Не использовать физические пределы сенсора вместо настроенного диапазона.

Если настроенный диапазон недоступен, оставлять поле пустым и показывать диагностическое объяснение.

## 4.4. Серийный номер

Реализовать чтение команд 14 и 16.

Различать:

- Номер сенсора.
- Номер окончательной сборки.
- Заводской серийный номер всего прибора.
- HART Device ID.

Номер из команды 16 разрешается помещать в поле «Серийный номер» автоматически только при наличии подтверждённого соответствия для конкретной модели или профиля производителя.

Если такого соответствия нет, сохранять номер как кандидат с указанием его происхождения, но не выдавать за подтверждённый заводской серийный номер.

Аналогично номер сенсора не считать серийным номером всего прибора без подтверждения.

При отсутствии достоверного заводского номера пользователь должен иметь возможность ввести его вручную со шильдика.

## 4.5. Дата изготовления

Приоритет форматов:

1. `15.07.2025` — известна полная дата.
2. `07.2025` — известны месяц и год.
3. `2025` — известен только год.
4. Пустое поле — достоверная дата неизвестна.

Для данных предусмотреть не только значение, но и точность даты: день, месяц или год.

Не заменять неизвестный день первым числом месяца.

Не заменять неизвестный месяц январём.

### Источник даты

Стандартное поле Date команды 13 не является гарантированной заводской датой изготовления.

Его нельзя автоматически записывать в графу «Дата выпуска» без подтверждения назначения в документации конкретной модели.

В будущем допускается использовать документированные команды производителя и профили датчиков для чтения заводских сведений.

В версии 0.4.0 реализовать расширяемый интерфейс для таких профилей, но не придумывать команды производителя.

Любые дополнительные команды должны быть документированными и безопасными командами чтения.

Если дата изготовления неизвестна, предоставить ручной ввод со шильдика или паспорта.

# 5. Происхождение и достоверность сведений

Для каждого паспортного поля внутри приложения сохранять:

- Значение.
- Тип источника.
- Номер HART-команды, если применимо.
- Исходное значение или HEX-представление.
- Время чтения.
- Признак ручного изменения.
- Степень подтверждения назначения поля.

Предлагаемые категории источников:

- Подтверждённое заводское поле.
- Стандартное поле HART.
- Подтверждённый профиль производителя.
- Введено пользователем.
- Нет данных.

Эти сведения нужны для предотвращения ошибочного использования HART Device ID или даты настройки как заводских паспортных характеристик.

В обычной Excel-ведомости технические метаданные показывать не требуется.

# 6. Отдельный режим «Обход датчиков»

Добавить отдельный экран или самостоятельный режим приложения.

Название:

**Обход датчиков**

Режим запускается по явному действию пользователя.

## 6.1. Начало обхода

Если VIATOR ещё не подключён:

- Предложить выбрать Bluetooth-коммуникатор.
- Получить подтверждение подключения.
- Установить SPP-соединение.
- Перейти в режим ожидания датчика.

Если VIATOR уже подключён:

- Использовать существующее соединение.
- Не требовать дополнительного подтверждения Bluetooth.

Одновременно активный обычный мониторинг и режим обхода запускать запрещено.

При переходе между режимами корректно завершать или приостанавливать прежнюю деятельность по решению пользователя.

## 6.2. Обнаружение прибора

Когда щупы подключены к датчику, приложение автоматически посылает разрешённый идентификационный запрос HART.

При получении корректного ответа:

- Идентифицирует устройство.
- Считывает необходимые паспортные сведения.
- Показывает карточку.
- Добавляет или обновляет строку временной ведомости.

Не начинать обычную длительную измерительную сессию.

Не сохранять график для каждого обнаруженного датчика.

## 6.3. Отсоединение щупов

Отсутствие HART-ответа после снятия щупов является ожидаемым событием режима обхода.

Не отображать аварийный диалог потери связи с датчиком.

Не запускать стандартный 60-секундный таймаут восстановления HART-сессии.

Показывать:

**Ожидание следующего датчика**

При этом:

- Bluetooth-соединение с VIATOR остаётся активным.
- Данные предыдущего датчика остаются в таблице.
- Приложение продолжает ожидать новый HART-ответ.
- Пользователю не нужно нажимать кнопку повторного опроса.

Отдельные кратковременные таймауты не должны создавать ложные записи или сбрасывать ведомость.

## 6.4. Подключение следующего датчика

При обнаружении другого уникального идентификатора выполнить новое чтение паспортных данных.

Предыдущие данные не удалять.

Новый прибор добавить в следующую строку ведомости.

Не объединять параметры разных приборов.

## 6.5. Защита от дубликатов

Основной ключ идентификации строить из производителя, типа устройства и уникального HART Device ID.

Если тот же прибор обнаружен повторно:

- Не создавать новую строку автоматически.
- При необходимости обновить автоматически прочитанные значения.
- Не стирать вручную введённые поля без отдельного решения пользователя.

Если настройки диапазона изменились между чтениями, обозначить изменение и предложить обновление строки.

Если у приборов выявлены одинаковые или недостоверные идентификаторы, не объединять их без проверки; предусмотреть ручное разделение записей.

## 6.6. Быстродействие

Главный приоритет — минимальное время между подключением щупов и появлением заполненной карточки.

Не выполнять ненужные измерительные циклы или длительные диагностические запросы.

Предусмотреть короткий настраиваемый интервал ожидания следующего датчика с разумной защитой от чрезмерной нагрузки HART-канала.

Не запускать многоточечное обнаружение или полный перебор адресов HART.

Текущий сценарий рассчитан на последовательное подключение к одному прибору на стандартном polling address 0.

Поддержку других индивидуальных адресов можно предусмотреть отдельно, не расширяя текущий этап до многоточечной сети.

# 7. Пользовательский интерфейс обхода

## 7.1. Основной экран

Показывать:

**Состояние коммуникатора**

- VIATOR подключён.
- VIATOR отключён.
- Bluetooth восстанавливается.

**Состояние HART**

- Ожидание датчика.
- Идентификация.
- Чтение данных.
- Данные получены.
- Ошибка чтения конкретного поля.

**Последний прочитанный прибор**

Компактная карточка:

- TAG.
- Производитель и модель.
- Серийный номер, если подтверждён.
- Дата выпуска, если известна.
- Настроенный диапазон.

**Накопленные результаты**

Список уже обнаруженных датчиков.

## 7.2. Редактирование

При нажатии на карточку открыть сведения о приборе.

Разрешить пользователю редактировать:

- TAG.
- Серийный номер.
- Дату выпуска.
- Марку / модель.
- При необходимости настроенный диапазон в локальной ведомости.

**Это только редактирование локальной записи.**

Никакие изменения не передаются в сам датчик.

При ручном редактировании отображать признак, что данные внесены пользователем.

Не путать редактор ведомости с будущим HART-конфигуратором.

## 7.3. Удобство обхода

Никаких обязательных модальных окон между датчиками.

Пользователь должен иметь возможность просто переставлять щупы.

После успешного считывания показывать краткое подтверждение и оставаться готовым к следующему прибору.

Если отдельное поле отсутствует, не блокировать дальнейший обход.

При необходимости добавить кнопку «Повторить чтение текущего прибора», но она не должна быть обязательной при каждом подключении.

# 8. Временная ведомость обхода

В течение одного обхода накапливать отдельную коллекцию результатов.

Каждая запись должна содержать:

- Внутренний ID строки.
- Идентификатор HART.
- Производителя.
- Тип устройства.
- TAG.
- Подтверждённый серийный номер или пустое поле.
- Дату выпуска с указанием её точности.
- Настроенный диапазон.
- Источники данных.
- Время идентификации.
- Статус полноты записи.

Накопление временных данных не равно автоматическому сохранению проверки в постоянный журнал.

Пользователь должен самостоятельно выбрать сохранение или экспорт.

Для защиты от потери результатов при сбое разрешается использовать временный локальный файл-черновик с возможностью восстановления после аварийного завершения приложения.

Черновик не должен автоматически превращаться в постоянную запись журнала.

Предусмотреть явное удаление черновика при завершении без сохранения.

# 9. Excel-ведомость (.xlsx)

Это обязательная функция версии 0.4.0.

Использовать **настоящий формат XLSX**, а не CSV, переименованный в XLSX.

Книга должна содержать **один лист**.

Название листа:

`Приборы`

## 9.1. Структура таблицы

Ровно пять основных видимых колонок:

| TAG | Серийный номер | Дата выпуска | Тип / марка датчика | Диапазон |
|---|---|---|---|---|

Каждый прибор — отдельная строка.

Не объединять все параметры одного прибора в одну ячейку.

Не создавать отдельный лист на каждый прибор.

Не добавлять историю измерений PV/SV/TV/QV в эту ведомость.

Не добавлять технические HART-поля, номера команд и диагностические HEX-данные в основные видимые столбцы.

## 9.2. Содержимое колонок

**TAG:** прочитанный или введённый TAG.

**Серийный номер:** достоверный серийный номер либо пустая ячейка.

**Дата выпуска:** дата с максимально доступной достоверной точностью.

**Тип / марка датчика:** человекочитаемый производитель и модель; если модель неизвестна, понятное обозначение с кодом типа.

**Диапазон:** одна строка вида `0…40 кПа`.

Если значение неизвестно, не заполнять его выдуманными сведениями.

## 9.3. Форматирование XLSX

- Каждое поле — самостоятельная ячейка.
- Одна строка заголовков.
- Автофильтры.
- Закрепление строки заголовков.
- Разумная ширина колонок.
- Удобочитаемый шрифт.
- Корректная кириллица.
- Серийные номера сохранять как текст, чтобы не терять ведущие нули.
- TAG также сохранять как текст.
- Даты сохранять без искажения точности.
- Не превращать неизвестный месяц или день в фиктивное число.
- Диапазоны отображать в ранее согласованном виде.

Для дат с различной точностью допустимо текстовое представление, сохраняющее ровно известные компоненты.

Ведомость должна открываться в Microsoft Excel и позволять пользователю редактировать, сортировать и фильтровать данные.

## 9.4. Экспорт

Добавить кнопку:

**Экспорт в Excel**

Она должна быть доступна:

- Во время активного обхода.
- После завершения обхода.
- При просмотре сохранённой ведомости.

При нажатии:

1. Сформировать файл XLSX.
2. Открыть стандартный механизм Android для сохранения или отправки.
3. Позволить выбрать файл и приложение-получатель.

Для экспорта не требуется завершать весь обход.

Не требовать доступа к интернету.

Не отправлять данные в облако автоматически.

## 9.5. Сохранение самой ведомости

Добавить возможность вручную сохранить результаты обхода внутри HART-бро.

Это самостоятельный вид записи, отличный от обычной измерительной сессии с графиком.

Пользователь может:

- Открыть сохранённую ведомость.
- Просмотреть приборы.
- Исправить данные.
- Экспортировать XLSX.
- Удалить ведомость с подтверждением.

Не смешивать результаты обхода с графиками измерительных сессий.

# 10. Поведение при потере связи

## 10.1. Потеря HART-ответов

В режиме обхода это штатная ситуация.

Переходить в ожидание нового датчика без аварийных диалогов.

Не очищать список приборов.

## 10.2. Потеря Bluetooth VIATOR

Считать отдельным событием.

Использовать существующий механизм автоматического восстановления Bluetooth до 60 секунд.

Показывать обратный отсчёт.

После восстановления возвращаться к ожиданию HART-датчика.

Не создавать дубликаты строк после повторного подключения коммуникатора.

Если Bluetooth не восстановлен, предложить продолжить обход после ручного подключения либо завершить его с сохранением или без сохранения результатов.

Не терять уже полученные данные при временном разрыве Bluetooth.

# 11. Работа в фоне

Режим обхода должен корректно работать при обычном переключении Android-приложений.

Bluetooth-соединение с VIATOR и состояние обхода должны принадлежать фоновой службе, а не жизненному циклу Activity.

При возвращении пользователь видит прежнюю ведомость и состояние ожидания либо чтения.

Если Android прекратил процесс, не утверждать, что измерение или обход продолжались.

Не создавать скрытую бесконечно работающую службу.

При явном завершении обхода останавливать необходимые фоновые операции и освобождать ресурсы.

# 12. Профили производителей и моделей

Создать расширяемую систему паспортных профилей.

Назначение профиля:

- Человекочитаемое название модели.
- Подтверждённые источники серийного номера.
- Подтверждённые источники даты выпуска.
- Особенности дополнительных безопасных команд чтения.
- Правила проверки полученных значений.

Начальные испытательные приборы:

**Метран-150**

- HART 7.
- Manufacturer `0x0099`.
- Device Type `0x9972`.
- Device ID испытанного прибора `5FCA7F`.

**Rosemount**

- HART 5.
- Manufacturer `0x0026`.
- Device Type `0x2662`.
- Device ID испытанного прибора `BF2C34`.
- Настроенный диапазон, полученный в предыдущем испытании: `0…10 кПа`.

Контрольные характеристики указанных приборов не зашивать в код в качестве постоянных значений.

Для каждого профиля использовать реальные спецификации конкретной модели.

Если нет документированного способа прочитать заводскую дату или серийный номер, не реализовывать фиктивную автоматическую расшифровку.

Не выполнять неизвестные команды производителя методом перебора.

Система профилей должна позволять добавлять новые модели в будущем без переработки пользовательского интерфейса обхода.

# 13. Автоматические тесты

Перед выпуском APK выполнить тесты на имитируемых HART-устройствах.

## 13.1. Чтение данных

- HART 5.
- HART 7.
- Команда 0.
- Команда 13.
- Команда 14.
- Команда 15.
- Команда 16.
- Команда 20 для поддерживаемых приборов.
- Неподдерживаемые команды.
- Пустые значения.
- Неизвестный производитель.
- Неизвестный тип устройства.
- Неверная длина кадра.
- Некорректный XOR.
- Неполные и фрагментированные ответы.

## 13.2. Бесшовное переключение

Симулировать последовательность:

1. Подключён прибор А.
2. Считаны параметры А.
3. HART-ответы исчезли.
4. Подключён прибор Б.
5. Считаны параметры Б.
6. Повторно подключён прибор А.
7. Проверено отсутствие дубликатов.

Отдельно проверить ситуацию, когда отсутствует ответ команды 14, 15 или 16, но команда 0 работает.

Смена прибора не должна приводить к зависанию или обязательному подтверждению.

## 13.3. Серийные номера

Проверить, что:

- HART Device ID не автоматически становится заводским номером.
- Sensor Serial Number не подменяет заводской номер всего прибора.
- Final Assembly Number используется как заводской номер только при подтверждённом назначении.
- Ручной ввод не затирается повторным чтением без согласования.
- Ведущие нули сохраняются.

## 13.4. Даты

Проверить:

- Полную дату.
- Месяц и год.
- Только год.
- Отсутствие даты.
- Некорректную дату.
- HART Date с неподтверждённым назначением.
- Ручной ввод.

Не преобразовывать дату настройки в дату производства автоматически.

## 13.5. Excel

Проверить:

- Один прибор.
- Несколько приборов.
- 100 приборов.
- Неизвестные паспортные поля.
- Разные единицы диапазонов.
- Отрицательные границы диапазонов.
- Русские символы.
- Серийные номера с ведущими нулями.
- Экспорт активного обхода.
- Повторный экспорт.
- Открытие файла стандартным Excel.

Использовать программную проверку структуры настоящего XLSX: один лист, пять основных колонок, корректные ячейки и значения.

Не считать успешное создание файла доказательством его корректного открытия, пока формат не проверен.

## 13.6. Регрессия

Повторно проверить обычный HART-мониторинг.

Не допустить нарушения:

- Идентификации Метрана.
- Чтения цифровых измерений.
- Графика.
- Работы в фоне.
- Сохранения обычных сессий.
- PDF/CSV.
- Существующего журнала.
- Восстановления Bluetooth.

# 14. План аппаратного испытания

Пользователь имеет ограниченный доступ к реальным приборам. Все проверки необходимо объединить в один испытательный сеанс.

Подготовить следующие действия.

**Тест 1. Метран-150**

Подключить VIATOR и запустить режим обхода.

Убедиться в автоматической идентификации и чтении диапазона.

Получить ответы команд 14 и 16 и сохранить HEX.

Проверить, какие номера реально возвращаются и можно ли сопоставить их с паспортными сведениями.

**Тест 2. Отсоединение щупов**

В безопасных условиях отключить HART-щупы.

Проверить переход в «Ожидание следующего датчика» без 60-секундного аварийного диалога.

Bluetooth VIATOR должен остаться подключённым.

**Тест 3. Второй прибор**

Подключить другой доступный HART-датчик.

Убедиться в автоматическом распознавании новой модели и появлении второй строки.

**Тест 4. Возврат к первому прибору**

Повторно подключить Метран.

Проверить отсутствие дубликата.

**Тест 5. Редактирование**

Внести тестовые паспортные данные вручную, если они отсутствуют в HART.

Проверить, что повторное чтение не удаляет их.

**Тест 6. Экспорт**

Создать XLSX с несколькими приборами.

Открыть его в Microsoft Excel и проверить столбцы, фильтрацию и редактирование.

**Тест 7. Фоновая работа**

Переключиться на другое Android-приложение и вернуться.

Проверить сохранность ведомости и состояние VIATOR.

**Тест 8. Диагностика**

Сохранить полный HEX-журнал с первой идентификацией, командами чтения паспортных данных и переходами между приборами.

Не изменять конфигурацию промышленных датчиков.

Перестановку щупов проводить только на разрешённых для подключения HART точках с соблюдением требований безопасности объекта. Не разрывать действующие измерительные цепи.

# 15. Ограничения текущего этапа

В версии 0.4.0 не реализовывать:

- Изменение диапазонов непосредственно в датчике.
- Запись TAG в датчик.
- Запись даты или серийного номера в HART-память.
- Калибровку.
- Сброс диагностических статусов.
- Произвольные команды записи.
- Многоточечный HART-опрос.
- USB OTG.
- Интеграцию ЭнИ-406.
- Автоматическую генерацию недостоверных паспортных сведений.

Редактирование локальной Excel-ведомости не является конфигурированием прибора.

# 17. Критерии приёмки

Версия 0.4.0 считается готовой к аппаратному испытанию, когда:

- VIATOR подключается один раз.
- Программа автоматически определяет последовательно подключаемые датчики.
- Не требует постоянного ручного запуска и завершения сессий.
- Не показывает аварийный таймаут при штатном снятии щупов.
- Считывает настроенный диапазон.
- Считывает доступные паспортные номера.
- Отличает заводские сведения от технических идентификаторов.
- Не выдаёт HART Date за дату изготовления без подтверждения.
- Позволяет вручную заполнить отсутствующие поля.
- Не создаёт дубликатов приборов.
- Сохраняет одну временную ведомость за обход.
- Экспортирует один лист XLSX с пятью согласованными колонками.
- Не нарушает работу существующего мониторинга.
- Не отправляет команды записи.
