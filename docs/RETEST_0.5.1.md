# Проверка повторной идентификации 0.5.1 на VIATOR

Автоматические сценарии перечислены в VALIDATION_0.5.1.md. Ниже — отдельная проверка на физическом коммуникаторе; она не считается выполненной в CI.

1. Установить опубликованный APK 0.5.1 поверх 0.5.0. Выбрать тот же VIATOR на «Связи», подключиться при отсутствии ответа датчика. После HART-таймаута ожидаются сообщение об ошибке идентификации, открытый Bluetooth и кнопка «Повторить опрос датчика». Измерительная сессия не начинается.
2. Подключить датчик и нажать кнопку. В HEX-журнале должен появиться новый TX команды 0 без нового RFCOMM connect/close; после корректного ответа — карточка прибора и доступный запуск сессии.
3. Повторить неудачную идентификацию, затем закрыть Bluetooth-связь со стороны коммуникатора. Индикатор приложения должен показать отсутствие Bluetooth. Повторный опрос должен самостоятельно подключиться к выбранному VIATOR и выполнить 0, без перезапуска приложения и повторного выбора устройства.
4. На экране ошибки свернуть/вернуть приложение, повернуть экран или пересоздать Activity. Кнопка повторного опроса должна остаться доступной. После удачного повтора Activity не должна создавать ещё одно соединение или автоматически начинать измерительную сессию.
5. При захвате неполного ответа 0 проверить HEX: кадр без последнего XOR не должен считаться успешной идентификацией. Поздние фрагменты после таймаута помечаются STALE; принятый новый кадр должен пройти проверку длины/XOR. Невозможно отличить полностью запоздавший корректный ответ той же команды/адреса после начала нового запроса: у HART нет номера транзакции.
6. В журнале повторной идентификации не должно появляться команды 35. Для отдельной подтверждённой настройки диапазона остаётся сценарий HARDWARE_TEST_0.5.0.md: одна передача 35 и проверочное чтение фактического результата.

Для отчёта сохранить версию APK, модель/ID датчика, сообщения интерфейса и HEX-журнал до/после повтора. После этого функциональный этап не расширяется.
